# Dungeon Crawler — Development Roadmap

Ordered by dependency, not necessarily by desire — each item is placed after
whatever it structurally relies on. Update this file as items are completed,
reordered, or new ideas come up.

Combat-lock bypass bug fixed — dev commands are now checked ahead of the `in_combat` branch in `main()`'s routing, so they always work regardless of combat state. *(Two bugs found and fixed during playtesting: (1) using an item mid-combat showed the enemy's counter-attack but no HP status line — `resolve_combat_round()` and the `use` branch had independently built similar messages and only one had the HP line; consolidated into a shared `format_hp_line(player, enemy)` helper so this can't drift apart a third time. (2) `dev spawn` was printing the raw `(message, None)` tuple instead of the message alone — a leftover call site that hadn't been updated to unpack the tuple after `handle_dev_command()`'s return type changed for teleport.)*

- [x] Expanded exploration commands — `examine` (alone) shows a room's `examine_text` and reveals any `Room.hidden_exits` (mirrors `locked_exits`'s dict pattern, promoted into `.exits` via `reveal_hidden_exits()` so `map`/`fullmap` needed zero changes); `examine <item>` reuses the existing `Item.description` rather than a new field. Sunken Vault's `down` exit from Styx Crossing is now the first hidden exit, revealed via examine rather than always visible. *(Design rule established here, worth keeping in mind generally: plain data goes straight into a constructor; anything needing another object to already exist — like `add_hidden_exit()` needing the target `Room` to exist first — has to stay a follow-up call.)*

- [x] XP and gold on kill / levelling system — `Enemy` gained `experience_reward`/`gold_reward` (both added to every existing enemy, tiered to match the earlier difficulty table), `Player` gained `gold`, `gain_experience()`, and `level_up()` (grants a skill point, rolls the XP threshold forward by ×1.5). `handle_enemy_defeat()` now takes `player` as a parameter and grants both rewards as part of its assembled message — every call site (`resolve_attack_and_check_defeat()`, `dev kill`) updated to match the new signature. Gold displays in `inventory`, not `stats`, since it isn't a character stat.

- [x] Intellect stat — lives on `Player` only (matches `experience`/`gold`, not `Character`), set by ancestry (`ANCESTRIES` gained an `intellect` field per entry — Athena highest at 5, Minotaur/Cyclops at 0, matching their brute-force flavour), grown by 1 automatically on every `level_up()`. `Room` gained `examine_text`/`required_intellect` (both plain constructor data); `handle_examine(room, player)` withholds the flavour text below the threshold but **always still reveals hidden exits regardless of Intellect** — the mechanical reveal is never gated, only the flavour text is, per the hard rule that Intellect must never block required progression. `get_stats()` now shows INT alongside the other core stats.

- [x] Docstrings and comments retrofit — every function/class/method now has a docstring (`pydocstyle` confirmed clean against the project's own convention, deliberately ignoring the stricter D205/D209/D400/D401 formatting opinions per `CLAUDE.md`'s "terse style, no ceremony" rule); D204 (blank line after a class docstring) fixed everywhere via a small script rather than 20 manual edits. Comments spot-checked in `combat.py`/`dev_tools.py` specifically, since those hold the most non-obvious design decisions. *(Two real logic issues were found and flagged along the way, deliberately not fixed here since this was a documentation-only pass — tracked separately, see the item right after this one.)*

- [x] Two logic issues from the docstring/comment retrofit — fixed. `handle_enemy_defeat()` no longer re-describes the defeat/loot text `Enemy.on_death()` already provides (avoiding duplication); it returns only the gold/XP message, which `resolve_attack_and_check_defeat()` now actually appends (guarded against a stray blank line on zero-reward defeats). `dev_tools.py`'s dead `STAT_ALIASES["skillpoints"]` entry removed, with a comment explaining why skill points need their own branch (nested under `player.skill_tree`, unreachable by the generic `setattr()` path).

## In order

1. **Enemy `choose_action()` + multiple enemies per room — decided to build as team-vs-team from the start.** Even though only the enemy side has multiple members right now, the combat-resolution loop should be written generically over two teams (the player's side, the enemies' side) rather than "one player vs. a list" — so Companions (#2) can slot in later as "add a second member to the player's team," not a rebuild of the combat loop. All active enemies act each round; the player can cycle/select a target.
2. **Companions** — allies who join and fight alongside you. Because #1 is being built team-vs-team from the start, this becomes "add to the player's team," not a new combat structure.
3. **Dodge ability** — a new Abilities-path skill, a chance to avoid an attack entirely, same shape as the flee-chance mechanic
4. **Armour split — helmet and body** — both slots equippable at once, replacing the single armour slot. *(Recommendation: keep `Character.armour` as a single derived/effective value — only `Player` computes it as the sum of its two equip slots; `Character`/`Enemy`/`take_damage()` don't need to change at all. **Resolved**: enemies currently only have a flat `armour`/DEF number, not real equippable armour, so nothing changes for `Enemy` here — but if enemies ever gain real armour items in future, they'll use this same helmet/body split for consistency, not a separate model.)*
5. **Armour durability + repair at the Forge of Prometheus** — depends on the armour split existing first
6. **Offensive/defensive status-effect items** — poison, flame, heal-over-time, ticking each turn in the combat loop. **Decided stacking rule, shared with Spells (#7)**: re-applying an already-active effect **prolongs its duration** (durations add together onto one ongoing effect — a 3-turn poison plus a fresh 2-turn application becomes one 5-turn poison, ticking at the normal single rate) — this is distinct from both "refresh only" and "stack as separate simultaneous instances" (which would double-tick during overlap); worth being precise about that distinction when this gets built.
7. **Spells (offensive/defensive)** — **decided resource model: a mana pool that recharges over time, plus a per-spell cooldown preventing the same spell being cast on consecutive turns** — a genuine hybrid, not mana-only. Needs a `cast` command; reuses the status-effect engine and stacking rule from #6 where relevant.
8. **Attack variety (light/heavy/ranged/spell) + refined turn economy** — a real action-selection step in combat rather than a single `attack` command, restricted by weapon type; alongside this, healing items stop ending your turn while offensive items and spells still do. **Decided heavy attack trade-off: a chance to miss, not a separate stamina resource** — higher damage output balanced by lower accuracy, no new resource needed. Placed after Spells since the "spell" attack option depends on it. A genuinely moderate-to-large addition, not a quick tweak — treat it as its own dedicated phase.
9. **Practice chamber (near the Forge of Prometheus, location flexible) with an infinitely-respawning, customisable practice dummy** — a player-facing sandbox for testing weapons/spells/potions, with the room granting infinite mana and no cooldowns while inside. Placed here specifically because it's only genuinely useful once spells, cooldowns, and attack variety (#7, #8) exist to test — building it earlier would mean testing against systems that don't exist yet. Effectively a player-facing counterpart to the dev tooling already built — worth reusing the same generic `dev set <stat> <value>` pattern (already built as part of dev tooling, see Completed) for the dummy's customisable stats, rather than a second, separate mechanism.
10. **Ancestry system, expanded — primary + secondary ancestor** — primary ancestor still sets starting stats (as now); a new secondary ancestor choice grants a distinct passive ability instead (no stat effect from the secondary pick — ability only). Viable, but only if secondary abilities are kept genuinely self-contained and never scale off primary-ancestor stats — that orthogonality is what avoids needing to balance all 110 primary/secondary combinations, reducing it to 11 stat profiles (done) and 11 independent abilities (new design work, roughly the scope of the three Abilities-path skills, times four). Same figure can't be picked as both. Abilities should be situational/conditional rather than flat power, to keep the "nothing essential, nothing useless" property intact.
11. **Save/load system — decided shape: 3 profiles, 5 save slots each, with delete and overwrite for both individual saves and whole profiles.** One file per save slot, one folder per profile (`saves/profile_N/slot_N.json` + a per-profile `achievements.json`) — deleting a save or profile becomes a simple file/folder removal, not a rewrite of a larger structure. **Key insight**: since `build_world()` already rebuilds the entire static map fresh every game start, a save file never needs to serialize the world graph (which would otherwise hit the circular-reference problem flagged in `PORTING_NOTES.md` — `Room.exits` pointing at other `Room` objects). Instead, only the *deltas* since world creation need saving: defeated enemies, taken items, opened locks, completed ally trades, enemy fled-from status (now in Completed — see the note there), and the Trophy Room's placed-trophies state (#17, added after this item was originally designed — a `Room.placed_trophies` set is exactly the same category of per-room persistent state as `locked_exits`, don't let it get missed when this is actually built), all trackable per room by name — replayed onto a freshly-built world on load, alongside the player's own serialized state. `PROFILE_LIMIT`/`SAVE_SLOTS_PER_PROFILE` are just constants, trivially changeable later. **Hard rule**: delete and overwrite (save or profile) must require explicit confirmation before executing — the one place in the game where a careless keystroke could destroy real progress. **Resolved: saving is checkpoint-only**, not freely available at any moment — the exact checkpoint locations/triggers are still to be decided, likely once the remaining floors (#13) are actually being built and it's clear where a checkpoint makes narrative/pacing sense.
12. **Multi-stage boss fights — decided design: no dedicated `Boss` class.** A boss is still a plain `Enemy` — the only new thing needed is an optional `next_phase_factory` attribute (a callable, following the existing `create_*()` factory pattern, e.g. `create_hades_phase_2`) rather than a subclass, since a phase transition is a data difference, not a behavioural one. Handled in defeat-handling (`handle_enemy_defeat()`), not inside `on_death()` itself — `on_death()`'s contract means "genuinely defeated," and a phase transition is a transformation, not a death, so keeping the two concepts separate matters. **Decided: transitions are seamless** — combat stays locked, `current_target` automatically updates to the next phase, no need to re-`attack`. Placed directly before "Finish remaining floors," since named late-game bosses (Hades, Typhon) are the actual reason this needs deciding before that content gets written, not after.
13. **Finish remaining floors** — the largest single item; deliberately last among core systems so content isn't built against mechanics that are still shifting. *(Note: a lifesteal weapon, dropped as loot later in the game, is small to build mechanically — same shape as the existing Thorns ability, just healing the attacker instead of hurting them — and fits naturally as content during this phase.)*
14. **Achievements, tied to a profile** — genuinely depends on save/load (#11) now, specifically the profile layer rather than individual save slots, so achievements persist across every playthrough under the same profile rather than resetting each new game. Placed after floors are finished, since that's when the full roster of things worth achieving actually exists.
15. **Carry weight / inventory cap** — gives real purpose to the existing `drop` command. Cheap to add: give `Item.__init__` a `weight: int = 1` default, so every existing item works unchanged and only items needing a non-default weight get individually tuned. **Quest items must be exempt from the cap** — same reasoning as the Intellect guardrail: nothing that can't be dropped should ever be able to block picking up something required. Placed after the floors are finished, since the mechanic only has real teeth once the full item roster exists to make carrying choices meaningful — and it pairs naturally with the shop that follows (carry capacity vs. what's worth selling is a classic pairing). **Decided shape**: a fixed base capacity for everyone, not a growing stat like HP/ATK — only ever modified by a one-time ancestry bonus and/or a skill/ability, never by levelling. Worth considering pairing a carry-weight bonus with combat-weaker ancestries (Poseidon, Medusa) as a form of non-combat compensation once real numbers are assigned. **Resolved: equipped gear still counts toward the cap** — equipping something doesn't remove it from the inventory, it just tags it `equipped`, so its weight is still genuinely being carried.
16. **Charon shop, gold currency, searchable chests** — gold itself already exists (see Completed — XP and gold on kill); this item is where it actually gets spent.
17. **Trophy room — decided shape: a physical room, not an ally-respect mechanic.** A new `Trophy(Item)` subclass (distinct from `QuestItem`), dropped only by named mini-boss/boss/mega-boss enemies via the existing `loot` mechanic — no new drop system needed. A dedicated Trophy Room with wall slots, one per trophy that exists in the game. A new `place <trophy>` command, valid only in that room, moves the item from inventory onto the room's display — reusing the same "room tracks its own completion state" pattern already used for `Ally.trade_completed`/`Room.locked_exits` (a `Room.placed_trophies: set[str]`). Placing every trophy that exists unlocks a chest. **Genuinely depends on both #13 (the full boss roster needs to exist so the total trophy count is known and every trophy is actually obtainable) and #16 (the payoff is specifically a chest, reusing that mechanic rather than duplicating it) — placed after both for that reason, later than Achievements/Carry Weight, which only needed the floors.**
18. **Standalone `.exe` build via PyInstaller** — `pyinstaller --onefile` bundles the whole game (interpreter included) into a single downloadable executable; no Pygame or "simulated terminal" needed, since it's the real terminal game, just packaged so a player doesn't need Python installed or the repo cloned. **Decided: automate via the existing GitHub Actions workflow** — extend it to build the `.exe` and attach it to the GitHub Release automatically whenever a version tag is pushed, rather than repackaging by hand for every release. Worth noting up front: a build is Windows-only per platform it's run on (a Mac/Linux build would need running the same step on those OSes too), file size will land in the 10–30MB range even for a small text game (the whole interpreter is bundled), and antivirus false positives on first run are a known, harmless quirk of PyInstaller specifically. Placed here, last among the "real" content/systems, since packaging a build only makes sense once the game genuinely feels complete enough to hand to someone as a finished download — everything above this (floors, achievements, carry weight, shop, trophy room) is what makes that true.
19. **Easter egg: UUDDLRLRBA input sequence** — grants a secret legendary item or activates God Mode. Genuinely trivial to build (a rolling buffer of recent raw inputs checked against the sequence each loop) and depends on nothing — placed late purely so it doesn't need rework as bigger systems land underneath it, not because it's hard.

## Long-term (sequenced against each other only, not the list above)
20. **Difficulty system** — a global stat multiplier applied at enemy creation, with narrow hardcoded overrides for specific bosses where a formula doesn't feel right (e.g. Charybdis)
21. **New Game+** — depends on the game having an ending (#13) and on the difficulty system (#20) to scale a replay
22. **Godot port** — see `PORTING_NOTES.md` for accumulated visual/UX ideas gathered along the way; deliberately last, once the Python version is fully finished

## Kept separate — not yet decided whether/when to build
- **Numbered command shortcuts** (`1` instead of `north`; bigger win for multi-word commands like `take mentor's token from mentor` than for movement)
- **Weak points / unarmoured critical hits** — would sit on top of the armour split (#4), since "unarmoured" only means something once armour has more than one slot
- **Lower-level enemy respawning after time** — genuinely undersized to place yet. The game currently has no concept of time/turns at all, and floor progression is mostly one-directional (`descend`-gated), so a player may never revisit a room a respawn would matter in. Worth deciding what "time" even means here (turn counter? actions taken?) and whether it's worth the cost given how little backtracking the game currently encourages, before this gets a slot in the ordered list. *(Note: the practice chamber's respawning dummy, #9, solves a related but distinct need — a controlled, respawn-on-defeat testing space — without needing to answer the harder "what does time mean in the wider world" question this item raises.)*
