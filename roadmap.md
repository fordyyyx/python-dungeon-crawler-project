# Dungeon Crawler — Development Roadmap

Ordered by dependency, not necessarily by desire — each item is placed after
whatever it structurally relies on. Update this file as items are completed,
reordered, or new ideas come up.

## Completed
- [x] Bug fixes (Chiron's hint reverting after trade, deflected damage not shown, unlocked skills not in `stats`, Wounded Soldier's hint not naming his items)
- [x] Combat loop consolidated into `resolve_attack_and_check_defeat()`
- [x] Toggleable auto-talk setting
- [x] Dev tooling — full command set built and working: generic `dev set <stat> <value>` (reads/writes any named `Player` attribute, so new stats like Intellect will work automatically with zero extra code), `dev add`, `dev spawn`, `dev remove`/`dev remove all`/`dev clear room` (three distinct removal scopes, none trigger loot), `dev kill` (reuses `handle_enemy_defeat()`), `dev teleport` (case-insensitive room lookup), `dev learn`, `dev unlock`/`dev unlock all`, floor-start selection via "developer mode" as a name. Combat-lock bypass bug fixed — dev commands are now checked ahead of the `in_combat` branch in `main()`'s routing, so they always work regardless of combat state. *(Two bugs found and fixed during playtesting: (1) using an item mid-combat showed the enemy's counter-attack but no HP status line — `resolve_combat_round()` and the `use` branch had independently built similar messages and only one had the HP line; consolidated into a shared `format_hp_line(player, enemy)` helper so this can't drift apart a third time. (2) `dev spawn` was printing the raw `(message, None)` tuple instead of the message alone — a leftover call site that hadn't been updated to unpack the tuple after `handle_dev_command()`'s return type changed for teleport.)*

## In order

1. **Enemy memory after fleeing** — a different room-entry message the second time you meet an enemy you've previously fled from. *(Note: once save/load exists, this "has been fled from" flag needs to be included in the delta-tracking model, #15 — don't forget it when building that system.)*
2. **Expanded exploration commands** — `examine` for extra flavour/hints (a new `Room`/`Item` text field), and hidden/secret exits (an exit that doesn't appear until revealed) — small, independent of everything else. Could replace the Sunken Vault's `down` exit as a first real use case. *(Recommendation: reuse the same dict-based pattern as `Room.locked_exits` for hidden exits — a `Room.hidden_exits: dict[str, Room]` promoted into `exits` once revealed — rather than inventing a new mechanism.)*
3. **XP and gold on kill / levelling system — decided to build together.** Enemies grant both `experience_reward` and `gold_reward` on defeat, added to `Enemy` at the same time even though the shop (gold's actual use, #19) is much later — avoids revisiting every `create_*()` enemy function twice. User-facing: XP shown in `stats`; a pickup message on kill (e.g. "Hero picked up 4 gold"); gold shown in the `inventory` display, not `stats`, since it isn't a character stat. `Player.level_up()` grants skill points, ties into the existing skill tree.
4. **Intellect stat** — a new stat, set by ancestry (same pattern as ATK/DEF/HP) and grown automatically on level-up rather than left static forever. Ties directly into `examine` (#2) — some hidden text/hints/secret doors only reveal themselves above a certain Intellect threshold. **Hard rule**: Intellect must never gate anything required to progress, only optional lore/discoveries — otherwise a low-Intellect pick risks becoming a genuine trap rather than a flavourful trade-off, breaking the same "nothing essential, nothing useless" principle already applied to ancestry.
5. **Enemy `choose_action()` + multiple enemies per room — decided to build as team-vs-team from the start.** Even though only the enemy side has multiple members right now, the combat-resolution loop should be written generically over two teams (the player's side, the enemies' side) rather than "one player vs. a list" — so Companions (#7) can slot in later as "add a second member to the player's team," not a rebuild of the combat loop. All active enemies act each round; the player can cycle/select a target.
6. **Companions** — allies who join and fight alongside you. Because #5 is being built team-vs-team from the start, this becomes "add to the player's team," not a new combat structure.
7. **Dodge ability** — a new Abilities-path skill, a chance to avoid an attack entirely, same shape as the flee-chance mechanic
8. **Armour split — helmet and body** — both slots equippable at once, replacing the single armour slot. *(Recommendation: keep `Character.armour` as a single derived/effective value — only `Player` computes it as the sum of its two equip slots; `Character`/`Enemy`/`take_damage()` don't need to change at all. **Resolved**: enemies currently only have a flat `armour`/DEF number, not real equippable armour, so nothing changes for `Enemy` here — but if enemies ever gain real armour items in future, they'll use this same helmet/body split for consistency, not a separate model.)*
9. **Armour durability + repair at the Forge of Prometheus** — depends on the armour split existing first
10. **Offensive/defensive status-effect items** — poison, flame, heal-over-time, ticking each turn in the combat loop. **Decided stacking rule, shared with Spells (#11)**: re-applying an already-active effect **prolongs its duration** (durations add together onto one ongoing effect — a 3-turn poison plus a fresh 2-turn application becomes one 5-turn poison, ticking at the normal single rate) — this is distinct from both "refresh only" and "stack as separate simultaneous instances" (which would double-tick during overlap); worth being precise about that distinction when this gets built.
11. **Spells (offensive/defensive)** — **decided resource model: a mana pool that recharges over time, plus a per-spell cooldown preventing the same spell being cast on consecutive turns** — a genuine hybrid, not mana-only. Needs a `cast` command; reuses the status-effect engine and stacking rule from #10 where relevant.
12. **Attack variety (light/heavy/ranged/spell) + refined turn economy** — a real action-selection step in combat rather than a single `attack` command, restricted by weapon type; alongside this, healing items stop ending your turn while offensive items and spells still do. **Decided heavy attack trade-off: a chance to miss, not a separate stamina resource** — higher damage output balanced by lower accuracy, no new resource needed. Placed after Spells since the "spell" attack option depends on it. A genuinely moderate-to-large addition, not a quick tweak — treat it as its own dedicated phase.
13. **Practice chamber (near the Forge of Prometheus, location flexible) with an infinitely-respawning, customisable practice dummy** — a player-facing sandbox for testing weapons/spells/potions, with the room granting infinite mana and no cooldowns while inside. Placed here specifically because it's only genuinely useful once spells, cooldowns, and attack variety (#11, #12) exist to test — building it earlier would mean testing against systems that don't exist yet. Effectively a player-facing counterpart to the dev tooling already built — worth reusing the same generic `dev set <stat> <value>` pattern (already built as part of dev tooling, see Completed) for the dummy's customisable stats, rather than a second, separate mechanism.
14. **Ancestry system, expanded — primary + secondary ancestor** — primary ancestor still sets starting stats (as now); a new secondary ancestor choice grants a distinct passive ability instead (no stat effect from the secondary pick — ability only). Viable, but only if secondary abilities are kept genuinely self-contained and never scale off primary-ancestor stats — that orthogonality is what avoids needing to balance all 110 primary/secondary combinations, reducing it to 11 stat profiles (done) and 11 independent abilities (new design work, roughly the scope of the three Abilities-path skills, times four). Same figure can't be picked as both. Abilities should be situational/conditional rather than flat power, to keep the "nothing essential, nothing useless" property intact.
15. **Save/load system — decided shape: 3 profiles, 5 save slots each, with delete and overwrite for both individual saves and whole profiles.** One file per save slot, one folder per profile (`saves/profile_N/slot_N.json` + a per-profile `achievements.json`) — deleting a save or profile becomes a simple file/folder removal, not a rewrite of a larger structure. **Key insight**: since `build_world()` already rebuilds the entire static map fresh every game start, a save file never needs to serialize the world graph (which would otherwise hit the circular-reference problem flagged in `PORTING_NOTES.md` — `Room.exits` pointing at other `Room` objects). Instead, only the *deltas* since world creation need saving: defeated enemies, taken items, opened locks, completed ally trades, and enemy fled-from status (#1), all trackable per room by name — replayed onto a freshly-built world on load, alongside the player's own serialized state. `PROFILE_LIMIT`/`SAVE_SLOTS_PER_PROFILE` are just constants, trivially changeable later. **Hard rule**: delete and overwrite (save or profile) must require explicit confirmation before executing — the one place in the game where a careless keystroke could destroy real progress. **Resolved: saving is checkpoint-only**, not freely available at any moment — the exact checkpoint locations/triggers are still to be decided, likely once the remaining floors (#16) are actually being built and it's clear where a checkpoint makes narrative/pacing sense.
16. **Finish remaining floors** — the largest single item; deliberately last among core systems so content isn't built against mechanics that are still shifting. *(Note: a lifesteal weapon, dropped as loot later in the game, is small to build mechanically — same shape as the existing Thorns ability, just healing the attacker instead of hurting them — and fits naturally as content during this phase.)*
17. **Achievements, tied to a profile** — genuinely depends on save/load (#15) now, specifically the profile layer rather than individual save slots, so achievements persist across every playthrough under the same profile rather than resetting each new game. Placed after floors are finished, since that's when the full roster of things worth achieving actually exists.
18. **Carry weight / inventory cap** — gives real purpose to the existing `drop` command. Cheap to add: give `Item.__init__` a `weight: int = 1` default, so every existing item works unchanged and only items needing a non-default weight get individually tuned. **Quest items must be exempt from the cap** — same reasoning as the Intellect guardrail: nothing that can't be dropped should ever be able to block picking up something required. Placed after the floors are finished, since the mechanic only has real teeth once the full item roster exists to make carrying choices meaningful — and it pairs naturally with the shop that follows (carry capacity vs. what's worth selling is a classic pairing). **Decided shape**: a fixed base capacity for everyone, not a growing stat like HP/ATK — only ever modified by a one-time ancestry bonus and/or a skill/ability, never by levelling. Worth considering pairing a carry-weight bonus with combat-weaker ancestries (Poseidon, Medusa) as a form of non-combat compensation once real numbers are assigned. **Resolved: equipped gear still counts toward the cap** — equipping something doesn't remove it from the inventory, it just tags it `equipped`, so its weight is still genuinely being carried.
19. **Charon shop, gold currency, searchable chests** — gold itself now arrives earlier, in #3, alongside XP; this item is where it actually gets spent.
20. **Easter egg: UUDDLRLRBA input sequence** — grants a secret legendary item or activates God Mode. Genuinely trivial to build (a rolling buffer of recent raw inputs checked against the sequence each loop) and depends on nothing — placed late purely so it doesn't need rework as bigger systems land underneath it, not because it's hard.

## Long-term (sequenced against each other only, not the list above)
21. **Difficulty system** — a global stat multiplier applied at enemy creation, with narrow hardcoded overrides for specific bosses where a formula doesn't feel right (e.g. Charybdis)
22. **New Game+** — depends on the game having an ending (#16) and on the difficulty system (#21) to scale a replay
23. **Godot port** — see `PORTING_NOTES.md` for accumulated visual/UX ideas gathered along the way; deliberately last, once the Python version is fully finished

## Kept separate — not yet decided whether/when to build
- **Numbered command shortcuts** (`1` instead of `north`; bigger win for multi-word commands like `take mentor's token from mentor` than for movement)
- **Weak points / unarmoured critical hits** — would sit on top of the armour split (#8), since "unarmoured" only means something once armour has more than one slot
- **Lower-level enemy respawning after time** — genuinely undersized to place yet. The game currently has no concept of time/turns at all, and floor progression is mostly one-directional (`descend`-gated), so a player may never revisit a room a respawn would matter in. Worth deciding what "time" even means here (turn counter? actions taken?) and whether it's worth the cost given how little backtracking the game currently encourages, before this gets a slot in the ordered list. *(Note: the practice chamber's respawning dummy, #13, solves a related but distinct need — a controlled, respawn-on-defeat testing space — without needing to answer the harder "what does time mean in the wider world" question this item raises.)*
