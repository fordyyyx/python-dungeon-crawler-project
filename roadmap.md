# Dungeon Crawler — Development Roadmap

Ordered by dependency, not necessarily by desire — each item is placed after
whatever it structurally relies on. Update this file as items are completed,
reordered, or new ideas come up.

## Completed
- [x] Bug fixes (Chiron's hint reverting after trade, deflected damage not shown, unlocked skills not in `stats`, Wounded Soldier's hint not naming his items)
- [x] Combat loop consolidated into `resolve_attack_and_check_defeat()`
- [x] Toggleable auto-talk setting
- [x] Enemy memory after fleeing — `Enemy.has_been_fled_from` flag, set in `flee_combat()`, checked in `print_room()` to vary the room-entry message on a repeat encounter. *(Note: still needs including in the save/load delta-tracking model once that's built.)*
- [x] `controls` command — always shows the full command list, checked ahead of the combat-lock branch (same as dev commands) so it's available regardless of state. Duplicates the README's Controls section by design (no shared source) — see `CLAUDE.md` for the reminder to keep both in sync.
- [x] Dev tooling — full command set built and working: generic `dev set <stat> <value>` (reads/writes any named `Player` attribute, so new stats like Intellect will work automatically with zero extra code), `dev add`, `dev spawn`, `dev remove`/`dev remove all`/`dev clear room` (three distinct removal scopes, none trigger loot), `dev kill` (reuses `handle_enemy_defeat()`), `dev teleport` (case-insensitive room lookup), `dev learn`, `dev unlock`/`dev unlock all`, floor-start selection via "developer mode" as a name, plus a dedicated blank Dev Test Room (registered in the `Map` via `build_dev_test_room()`, not added to any floor's room dict, reachable purely via `dev teleport dev test room`). Combat-lock bypass bug fixed — dev commands are now checked ahead of the `in_combat` branch in `main()`'s routing. *(Two bugs found and fixed during playtesting: (1) using an item mid-combat showed the enemy's counter-attack but no HP status line — consolidated into a shared `format_hp_line()` helper. (2) `dev spawn` was printing the raw `(message, None)` tuple instead of the message alone.)*
- [x] Expanded exploration commands — `examine` (alone) shows a room's `examine_text` and reveals any `Room.hidden_exits`; `examine <item>` reuses the existing `Item.description` rather than a new field.
- [x] XP and gold on kill / levelling system — `Enemy` gained `experience_reward`/`gold_reward`, `Player` gained `gold`, `gain_experience()`, and `level_up()` (grants a skill point, rolls the XP threshold forward by ×1.5). `handle_enemy_defeat()` now takes `player` as a parameter and grants both rewards.
- [x] Intellect stat — lives on `Player` only, set by ancestry, grown by 1 automatically on every `level_up()`. `Room` gained `examine_text`/`required_intellect`. ***Revised since*** — the original rule ("Intellect never gates required progress") was tightened: Intellect *can* gate progress, including the hidden-exit reveal itself, since it grows every level with no cap and nothing is ever permanently unreachable.
- [x] Docstrings and comments retrofit — every function/class/method now has a docstring.
- [x] Enemy `choose_action()` + multiple enemies per room — built as team-vs-team from the start: combat resolution works over `player_team`/`enemy_team` plain lists (no `Team` class), player acting first each round followed by every still-living enemy via the standalone `choose_enemy_action()`. Utility-based scoring (`_score_candidate_actions()` plus random noise) across three actions: Attack, Defend/Brace, Heal. New player-facing `target <name>`/`target <name> <number>` command, with stable disambiguation numbering; `format_hp_line` generalized to a full N-combatant display. **Known follow-up, fix decided and now built** (see `CLAUDE.md`): Defend's score redefined around genuine incoming danger rather than raw missing-HP%.
- [x] **Companions** — `Companion(Character)` (real combat stats, unlike the stat-less `Ally`), holding `home_room`, `required_items`, and the same `aggression_weight`/`caution_weight`/`randomness_weight`/`brace_amount`/`heal_amount` fields as `Enemy`. `Player.companion` is a plain attribute; a new `Player.team` property returns `[player]` or `[player, companion]` (automatically excluding a downed companion, `hp == 0`). `recruit_companion()`/`dismiss_companion()` (`exploration.py`) mirror `trade_with_ally()`'s exact item-consumption mechanics, routed via `recruit <name>`/`dismiss`. `choose_companion_action()`/`choose_companion_target()` (`combat.py`) mirror `choose_enemy_action()`/`choose_enemy_target()` — separate functions per `CLAUDE.md`'s decision, though the underlying per-candidate scoring is fully shared. A downed companion isn't dead — `on_death()` returns a distinct "downed, recoverable" message; `Reviver(Consumable)` restores them, and dismissing a downed companion also restores them to full HP as a free alternative to a Reviver. `engine.py`'s `attack` handler now passes `player.team`, not a hardcoded `[player]`, so enemies can genuinely target a companion. *(Known gap: `dev spawn` has no companion lookup yet, and no room in `build_world()` places a recruitable `Companion`, so a successful `recruit` isn't reachable through `main()` at all right now. Worth closing before this gets exercised by real content.)*
- [x] **Dodge ability** — new Abilities-path skill (`DodgeSkill`), a flat, additive `Character.dodge_chance: float` (default `0.0`, same precedent as `has_thorns`/`brace_amount`) checked at the very top of `take_damage()` — a successful roll (`random.random() < self.dodge_chance`) short-circuits the entire method, returning `0, "<name> dodges the attack!"` before any Defend/Brace or armour math runs, so a dodge means the hit never landed at all rather than being reduced to zero. Fourth skill in the Abilities path, alongside Double Strike/Thorns/Last Stand — deliberately breaks the 3/3/4 symmetry with Attack/Defence, accepted as fine. Shipped as "Nimble Grace," 15% chance.

## In order

1. **Armour split — helmet and body** — both slots equippable at once, replacing the single armour slot. *(Recommendation: keep `Character.armour` as a single derived/effective value — only `Player` computes it as the sum of its two equip slots; `Character`/`Enemy`/`take_damage()` don't need to change at all. **Resolved**: enemies currently only have a flat `armour`/DEF number, not real equippable armour, so nothing changes for `Enemy` here — but if enemies ever gain real armour items in future, they'll use this same helmet/body split for consistency, not a separate model.)*
2. **Armour durability + repair at the Forge of Prometheus** — depends on the armour split existing first
3. **Offensive/defensive status-effect items** — poison, flame, heal-over-time, ticking each turn in the combat loop. **Decided stacking rule, shared with Spells (#4)**: re-applying an already-active effect **prolongs its duration** (durations add together onto one ongoing effect) — distinct from both "refresh only" and "stack as separate simultaneous instances."
4. **Spells (offensive/defensive)** — **decided resource model: a mana pool that recharges over time, plus a per-spell cooldown preventing the same spell being cast on consecutive turns**. Needs a `cast` command; reuses the status-effect engine and stacking rule from #3 where relevant.
5. **Attack variety (light/heavy/ranged/spell) + refined turn economy** — a real action-selection step in combat rather than a single `attack` command, restricted by weapon type; healing items stop ending your turn while offensive items and spells still do. **Decided heavy attack trade-off: a chance to miss, not a separate stamina resource.** Placed after Spells since the "spell" attack option depends on it.
6. **Practice chamber (near the Forge of Prometheus, location flexible) with an infinitely-respawning, customisable practice dummy** — a player-facing sandbox for testing weapons/spells/potions, with the room granting infinite mana and no cooldowns while inside. Placed here since it's only genuinely useful once spells, cooldowns, and attack variety (#4, #5) exist to test. Reuses the same generic `dev set <stat> <value>` pattern for the dummy's customisable stats.
7. **Ancestry system, expanded — primary + secondary ancestor** — primary ancestor still sets starting stats; a new secondary ancestor choice grants a distinct passive ability instead (no stat effect from the secondary pick — ability only). Viable, but only if secondary abilities stay genuinely self-contained and never scale off primary-ancestor stats. Same figure can't be picked as both.
8. **Save/load system — decided shape: 3 profiles, 5 save slots each, with delete and overwrite for both individual saves and whole profiles.** One file per save slot, one folder per profile (`saves/profile_N/slot_N.json` + a per-profile `achievements.json`). **Key insight**: since `build_world()` rebuilds the entire static map fresh every game start, a save file never needs to serialize the world graph — only the *deltas* since world creation: defeated enemies, taken items, opened locks, completed ally trades, enemy fled-from status, and the Trophy Room's placed-trophies state (#13, a `Room.placed_trophies` set — same category of per-room persistent state as `locked_exits`, don't let it get missed). `PROFILE_LIMIT`/`SAVE_SLOTS_PER_PROFILE` are just constants, trivially changeable later. **Hard rule**: delete and overwrite must require explicit confirmation before executing. **Resolved: saving is checkpoint-only** — exact checkpoint locations/triggers still to be decided, likely once the remaining floors (#10) are being built.
9. **Multi-stage boss fights — decided design: no dedicated `Boss` class.** A boss is still a plain `Enemy` — the only new thing needed is an optional `next_phase_factory` attribute (a callable, following the existing `create_*()` factory pattern) rather than a subclass. Handled in defeat-handling (`handle_enemy_defeat()`), not inside `on_death()` itself. **Decided: transitions are seamless** — combat stays locked, `current_target` automatically updates to the next phase. Placed directly before "Populate all floors," since named late-game bosses (Hades, Typhon) are the actual reason this needs deciding before that content gets written.
10. **Populate all floors — enemies, allies, items, and trades, into the shell built via `build_floor_2()` through `build_floor_9()`.** Still deliberately last among core systems, since this genuinely depends on every mechanic (combat, items, skills, spells) being finalized first. *(Note: a lifesteal weapon, dropped as loot later in the game, fits naturally as content during this phase.)*
11. **Achievements, tied to a profile** — genuinely depends on save/load (#8), specifically the profile layer. Placed after floors are finished, since that's when the full roster of things worth achieving actually exists.
12. **Carry weight / inventory cap** — gives real purpose to the existing `drop` command. Cheap to add: give `Item.__init__` a `weight: int = 1` default. **Quest items must be exempt from the cap.** Placed after the floors are finished. **Decided shape**: a fixed base capacity for everyone, only ever modified by a one-time ancestry bonus and/or a skill/ability, never by levelling. **Resolved: equipped gear still counts toward the cap.**
13. **Trophy room — decided shape: a physical room, not an ally-respect mechanic.** A new `Trophy(Item)` subclass, dropped only by named mini-boss/boss/mega-boss enemies via the existing `loot` mechanic. A dedicated Trophy Room with wall slots, one per trophy that exists in the game. A new `place <trophy>` command, valid only in that room (`Room.placed_trophies: set[str]`). Placing every trophy unlocks a chest. **Genuinely depends on both #10 (full boss roster) and #14 (the chest payoff) — placed after both for that reason.**
14. **Charon shop, gold currency, searchable chests** — gold itself already exists (see Completed — XP and gold on kill); this item is where it actually gets spent.
15. **Standalone `.exe` build via PyInstaller** — `pyinstaller --onefile` bundles the whole game into a single downloadable executable. **Decided: automate via the existing GitHub Actions workflow** — extend it to build the `.exe` and attach it to the GitHub Release automatically on a version tag push. Windows-only per platform it's run on; file size 10–30MB; antivirus false positives are a known, harmless PyInstaller quirk. Placed last among the "real" content/systems.
16. **Easter egg: UUDDLRLRBA input sequence** — grants a secret legendary item or activates God Mode. Genuinely trivial to build, depends on nothing — placed late purely so it doesn't need rework as bigger systems land underneath it.

## Long-term (sequenced against each other only, not the list above)
17. **Difficulty system** — a global stat multiplier applied at enemy creation, with narrow hardcoded overrides for specific bosses where a formula doesn't feel right (e.g. Charybdis)
18. **New Game+** — depends on the game having an ending (#10) and on the difficulty system (#17) to scale a replay
19. **Unreal Engine port (C++)** — see `PORTING_NOTES.md` for accumulated visual/UX ideas gathered along the way; deliberately last, once the Python version is fully finished. **Decided over Godot**: the original appeal of Godot was GDScript's Python-like syntax, but with C++ as the actual goal, Unreal's native, mature C++ workflow is a better fit than fighting Godot's less-common C++ path (GDExtension).

## Kept separate — not yet decided whether/when to build
- **Numbered command shortcuts** (`1` instead of `north`; bigger win for multi-word commands like `take mentor's token from mentor` than for movement)
- **Weak points / unarmoured critical hits** — would sit on top of the armour split (#1), since "unarmoured" only means something once armour has more than one slot
- **Lower-level enemy respawning after time** — genuinely undersized to place yet.
