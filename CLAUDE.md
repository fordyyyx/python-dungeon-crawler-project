# Project Context for Claude Code

## What this project is
A text-based dungeon crawler RPG in pure Python, Greek mythology themed, built as an OOP portfolio project. The person building this is a first-year Computer Science student — code should stay readable and instructive, not overly clever or terse.

## Code style
- **British English spelling** in all identifiers, comments, and strings — `armour` not `armor`, `defence` not `defense`, `colour` not `color`, etc.
- `src/` layout: source lives in `src/dungeon_crawler/`, tests in `tests/`
- One responsibility per module (current, post-reorganisation structure — see the "Reorganise engine.py" item in roadmap.md's Completed section for how this came about):
  - `characters.py` — `Character`, `Player`, `Enemy`, `Ally`, `Companion`, `Skill`, `SkillPath`, `SkillTree`
  - `items.py` — `Item`, `Weapon`, `Armour`, `Consumable`, `QuestItem`, `Inventory`, plus `Consumable`'s own subclasses `Reviver`, `StatusEffectItem`, `SpellBook`, `SkillPointReward`. *(A real bug found and fixed: `SkillPointReward` used to inherit `Item` directly, so `Inventory.use_item()`'s `isinstance(item, Consumable)` check never matched it - it silently stayed in the inventory forever after being used. Fixed by making it inherit `Consumable` instead, same as its siblings.)*
  - `world.py` — `Room`, `Map`
  - `content/` (a package, formerly a single `content.py`) — actual game content (instances, not class definitions), one module per floor (`floor_0.py` … `floor_9.py`, each holding that floor's `create_*()` factories plus its `build_floor_N()`), assembled by `build_world()` (`world_builder.py`). Also `common.py`, `dev_content.py` (dev-only `create_test_*()` content and the blank/companion test rooms), and `ancestries.py` (`ANCESTRIES`, the ancestry-selection data). See "Content package layout" below.
  - `combat.py` — combat resolution: `resolve_combat_round`, `resolve_attack_and_check_defeat`, `resolve_pending_defeats`, `resolve_companion_and_enemy_turns`, `tick_start_of_turn_if_needed`, `handle_enemy_defeat`, `format_hp_line`, `flee_combat`, `get_duel`, `restore_duel_hp`, `end_duel`, `protect_duel_loser`, `handle_combat_command`, `get_enemy_display_name`, `handle_target_command`, `choose_enemy_action`/`choose_enemy_target`/`_score_candidate_actions`, `choose_companion_action`/`choose_companion_target`/`_score_companion_candidate_actions` (utility-based AI, both enemy and companion — see "Enemy AI and team combat" below)
  - `exploration.py` — everything outside combat: `pick_up`, `take_all`, `take_all_from_ally`, `check_equippable`, `trade_with_ally`, `recruit_companion`, `dismiss_companion`, `repair_item`, `is_exit_locked`, `get_exit_guardian`, `display_local_exits`, `display_map`, `find_floor_for_room`, `handle_examine`, `has_unfinished_trade`, `get_uncleared_reasons`, `get_undiscovered_rooms`, `get_uncleared_rooms`, `start_duel`
  - `character_creation.py` — `choose_ancestry`, `choose_secondary_ancestry`, `create_player`, `choose_title_screen_action`, `choose_profile`, `choose_slot`, `choose_occupied_slot`, `confirm` (the last five drive the title screen and every save/load prompt — see "Save/load system and the title screen" below)

Gated by `player.dev_mode` (`characters.py`), but that check lives in `main()`'s routing, not in this module. **One deliberate exception**: `handle_dummy_set()` lives here too (it shares `_apply_stat()` with `handle_dev_set()`), but it is a normal player command, not gated by `player.dev_mode` at all - see "Practice Chamber and respawning enemies" below.
  - `engine.py` — now genuinely slim: `main()`'s loop and top-level command routing only, plus `print_room()` and `get_controls_text()` (both tightly coupled to the loop itself, not moved elsewhere)
  - `status_effects.py` — `StatusEffect` (poison/flame/heal-over-time; ticked via `Character.tick_status_effects()` — see "Status effects and spellcasting" below)
  - `spells.py` — `Spell` (offensive/defensive/utility spellcasting; cast via `handle_combat_command()`'s `cast <spell>` branch — see "Status effects and spellcasting" below)

The full codebase now has docstrings on every function/class/method, confirmed via `pydocstyle --convention=pep257` (deliberately ignoring D205/D209/D400/D401 — those are formatting opinions stricter than this project's own convention, not gaps). ## Canonical attribute names — do not drift from these
- `Character.attack_damage` — **not** `attack_power`. This project has used `attack_power` inconsistently in earlier design discussion; `attack_damage` is the real, current name. Always check the actual file before assuming.
- `Character.hp`, `Character.max_hp` — as expected.
- `Character.armour` — **a computed property, not a stored number.** It returns `base_armour + equipment_defence()`: `Character.base_armour` is armour that doesn't come from worn gear (an enemy's natural armour, ancestry, Defence skills, `dev set def`/`dummy set def`), and `equipment_defence()` sums every worn, unbroken piece (a broken one counts only with Unyielding Tide). The setter adjusts `base_armour` so the total comes out right, so `armour += bonus` (`DefenceBoostSkill`) still works unchanged. **Never add or subtract a piece's `defence` by hand** - equipping, unequipping, breaking and repairing all change the total automatically. See "Armour slots and durability" below.
- `Character.has_double_strike`, `Character.has_thorns`, `Character.has_last_stand` — ability flags, live on `Character` (not `Player`), since `Enemy` could plausibly use them too.
- `Character.take_damage(amount, attacker=None, ignore_armour=False, armour_pierce=0)` — `ignore_armour` skips the armour subtraction only (brace and Iron Hide still apply); only Double Strike's second hit passes it. `armour_pierce` lowers the armour applied, never below `0` - passed from a piercing weapon's `Weapon.armour_pierce`. See "Minimum damage" below for `MINIMUM_DAMAGE`.
- `Character.pending_damage_reduction` — **built.** Generic flat damage-reduction value, consumed (and reset to `0`) the next time `take_damage()` runs on this character. Lives on `Character`, not `Enemy`, since `take_damage()` doesn't know which subclass `self` is; `Enemy.brace_amount` is just the fixed value that populates it when Defend is chosen.
- `Player.ancestry_label` — set at character creation, displayed in `get_stats()`.
- `Player.intellect` — **Player-only**, not on `Character`. Matches `experience`/`gold`'s precedent, not the ability flags' — nothing currently reads an enemy's or ally's intellect, so it doesn't belong on the shared base class. Set by ancestry (`ANCESTRIES["intellect"]`), grows by 1 on every `level_up()`.
- `HP_PER_LEVEL = 2` (`characters.py`) - `Player.level_up()` raises `max_hp` by this much, and raises current `hp` by the same amount rather than healing to full, so a mid-fight level-up is never a free full restore. **Max HP grows now** - until this existed, a player's HP was fixed at their ancestry's starting value for the whole game.
- `Player.companion` — plain attribute, `Companion | None`. `Player.team` is a **property** returning `[player]` or `[player, companion]` (a downed companion, `hp == 0`, is automatically excluded).
- **Enemy AI fields — all built**: `Enemy.aggression_weight`, `Enemy.caution_weight`, `Enemy.randomness_weight` (utility-scoring weights, defaulting to `1.0`/`1.0`/`0.3`), `Enemy.brace_amount` (flat damage reduction from Defend, default `0`), `Enemy.heal_amount` (flat HP restored by Heal, default `0` — `0` excludes Heal from the candidate list entirely, see "Enemy AI and team combat" below). All plain data, same precedent as `experience_reward`/`gold_reward`, set per `create_*()` call; every existing call works unchanged thanks to the defaults. Tune specific enemies' actual values as part of "Populate all floors," not before.
- `Enemy.respawns` — **built.** `bool`, default `False`. Not an AI field - read by `handle_enemy_defeat()`/`resolve_pending_defeats()` (`combat.py`), not by the scoring functions above. See "Practice Chamber and respawning enemies" below.
- `Enemy.defeat_effect` — **built.** `Callable[[Player], str] | None`, default `None`. Run once when the enemy is finally defeated (never on an intermediate boss phase or wave), and its returned line is appended to `handle_enemy_defeat()`'s message. Built as a callable rather than the originally planned `defeat_text: str`, so it can *do* something as well as say something. First used by the Shade of Achilles' duel form (grants a skill point); Hades' final phase will carry the Typhon reveal in it (roadmap.md's "Story reveal hooks") - never a name check.
- `Enemy.duel_companion: Companion | None` / `Enemy.duel_return_hp: int | None` — **built**, both default `None`. Set only by `start_duel()` on a companion's combat form: the companion to put back in the room when the duel ends, and the player's HP to restore. See "Companion duels and levelling" below.
- **Drop chance on respawning enemies** — **planned, not built** (roadmap.md's "Drop chance on respawning enemies" item). Working name `Enemy.drop_chance: float = 0.0`; the name isn't locked in yet, so check roadmap.md before building.
- `Room.locked_exits: dict[str, str]` / `Room.unlock_exit(direction)` — **built.** direction -> the item needed to pass. `unlock_exit()` removes the lock for good; `main()` calls it the first time the player walks through, and `save_system.py` saves the directions still locked. See "Locked exits open for good" below.
- `Room.guarded_exits: set[str]` — **built.** Directions that can't be used while any living, non-`respawns` enemy remains in the room. Set via `Room.guard_exit(direction)`, checked via `get_exit_guardian()` (`exploration.py`). See "Guarded exits" below.
- `Room.is_practice_chamber` — **built.** `bool`, default `False`. Only the Practice Chamber (floor 2, next to the Forge of Prometheus) is one. Gates free spellcasting in `handle_combat_command()`'s `cast` branch - see "Practice Chamber and respawning enemies" below.
- `Companion` mirrors `Enemy`'s AI fields exactly (`aggression_weight`/`caution_weight`/`randomness_weight`/`brace_amount`/`heal_amount`), plus `home_room` and `required_items`.
- `Companion` dialogue and duels — **built.** `hint`/`hint_recruitable` (`talk()` returns `hint_recruitable` once nothing blocks recruiting, otherwise `hint`, otherwise `"<name> has nothing to say."`), `duel_enemy_factory: Callable[[], Enemy] | None`, `duel_won: bool`, `duel_won_message`/`duel_lost_message`, and the `requires_duel` property (`duel_enemy_factory is not None and not duel_won`). All data on the companion - no name checks.
- `Companion.level`/`experience`/`experience_to_next_level` — **built.** Same curve as the player (`STARTING_EXPERIENCE_TO_NEXT_LEVEL = 50`, ×1.5 per level). Each level adds `COMPANION_HP_PER_LEVEL = 2` max HP and `COMPANION_ATTACK_PER_LEVEL = 1` attack (`characters.py`). `restore_level(level, experience)` rebuilds this on load.
- `Character.equipped_helmet`, `Character.equipped_body`, `Character.equipped_shield` — **built**, replacing the old single `equipped_armour`. Three independent `Armour | None` slots; `Armour.slot` (`"body"` default, `"helmet"`, or `"shield"` - anything else raises `ValueError`) decides which one `use()`/`unequip()` read and write via `getattr`/`setattr(character, f"equipped_{slot}")`. See "Armour slots and durability" below.
- `Armour.weight` — **built.** `"light"` (default), `"medium"`, or `"heavy"` (anything else raises `ValueError`). Adds `ARMOUR_WEIGHT_MISS_PENALTY[weight]` (`0.0`/`0.05`/`0.10`) to every attack the wearer makes - see "Weapon classes, armour weight, and miss chance" below.
- `Character.equipped_melee_weapon`, `Character.equipped_ranged_weapon` — **built**, replacing the old single `equipped_weapon`. Two independent `Weapon | None` slots, same shape as `equipped_helmet`/`equipped_body`; `Weapon.slot` (`"melee"` default, or `"ranged"`) decides which one `use()`/`unequip()` read and write via `getattr`/`setattr(character, f"equipped_{slot}_weapon")`. Unlike `Armour`, a weapon's `damage` is **not** accumulated into `Character.attack_damage` - it's read directly off the matching slot at attack time instead. See "Weapon slots and attack variety" below.
- `Weapon.weapon_class` — **built.** `"blade"` (default), `"heavy"`, `"piercing"`, or `"ranged"` (anything else raises `ValueError`); `Weapon.two_handed` is a property, `True` for `"heavy"`. Plus four signature properties, all read off the equipped weapon inside `attack()`, never copied onto the character as flags: `armour_pierce: int = 0`, `lifesteal: bool = False`, `poison_chance: float = 0.0`, `cleave: bool = False`. See "Weapon classes, armour weight, and miss chance" below.
- `Item.details() -> str` — **built.** A short stat summary for the inventory display - `""` by default, overridden by `Weapon` (e.g. `"heavy, two-handed, cleave, 7 DMG"`) and `Armour` (e.g. `"body, heavy, 6 DEF, 18/18 durability"`).
- `Character.dodge_chance` — **built.** Flat, additive `float` (default `0.0`), same precedent as `pending_damage_reduction`/`brace_amount`. Checked at the very top of `take_damage()`, before anything else runs — a successful roll means the hit never landed at all, not that it was reduced to zero. Set by `DodgeSkill`.
- `Character.has_lifesteal` — **built.** `bool`, default `False`. In `Character.attack()`, after damage is dealt: heals the attacker for `damage_dealt // 2` (capped at `max_hp`), skipped entirely if no damage was dealt (e.g. blocked by armour, or dodged). Player-facing message appends `"<name> drains <n> HP from the wound."`. Granted per-`Enemy` via a constructor field (`Enemy.__init__`'s `has_lifesteal` parameter) - Lamia (floor 4, Shadowy Corner) is the first and so far only enemy with it set. A lifesteal *weapon* exists too - Lamia's Fang (`Weapon.lifesteal`) - but it never sets this flag: `attack()` checks `self.has_lifesteal or weapon.lifesteal`, so unequipping the Fang can't wipe a flag something else granted. **Only a weapon's heal is capped**, at `WEAPON_LIFESTEAL_CAP = 3` (`characters.py`); innate lifesteal never is. The cap applies only when `self.has_lifesteal` is `False`, so a character with both heals once, uncapped - the two never stack.
- **Ten secondary-ancestor ability flags — all built**: `has_reckless_strength`, `has_measured_casting`, `has_swift_feet`, `has_unyielding_tide`, `has_berserking`, `has_silver_tongue`, `can_ranged_without_weapon`, `has_petrifying_gaze`, `has_bull_rush`, `has_iron_hide` (all `bool`, default `False`, live on `Character`). Granted once at character creation via `ANCESTRIES`, never by the skill tree. See "Secondary ancestry abilities" below for what each one does and where it's checked.
- `Player.secondary_ancestry_label` — **built.** `str`, default `""`. Set by `create_player()`, displayed in `get_stats()`. See "Secondary ancestry abilities" below.
- `Character.active_effects: list[StatusEffect]` — **built.** Every currently-active status effect on this character. Managed via `apply_status_effect()`/`tick_status_effects()` — never append/remove directly. See "Status effects and spellcasting" below.
- `Player.mana`, `Player.max_mana` — **built.** Both default `20`. Spent by `cast <spell>`, recovered via `rest`/`wait` (`REST_MANA_AMOUNT` per use, `engine.py`) — no passive per-turn regen.
- `Player.known_spells: list[Spell]`, `Player.spell_cooldowns: dict[str, int]` — **built.** Spells are taught permanently via `SpellBook`; cooldowns are keyed by spell name, ticked down by `Player.tick_spell_cooldowns()`.
- `Player.visited_floors: set[str]` — **built.** Which of `build_world()`'s floor-key names (e.g. `"floor_0"`) this run has reached, checked via `find_floor_for_room()` (`exploration.py`) — **not** a `Room.floor` field (tried, then removed as redundant). Drives `main()`'s autosave. See "Save/load system and the title screen" below.
- `Player.visited_rooms: set[str]` — **built.** Names of every room this run has entered (added on every successful move in `main()`, plus the starting room). Read only by the `uncleared` command, which reports these rooms plus their immediate open neighbours - never anything further away. `dev teleport` doesn't add to it.
- `Player.auto_map: bool` — **built**, default `False`. When on, `print_room()` lists the room's exits on entry. Toggled via `toggle auto map`, mirroring `auto_talk`.
- `Player.seen_hints: set[str]` — **built**, default empty. Keys from `hints.HINTS` already shown in this save; `show_hint()` adds to it. Saved, so a reload never repeats a hint.
- `Ally.hint_traded: str` — **built**, default `""`. What the ally says once `trade_completed` is `True`. `Ally.talk()` now picks, in priority order: `hint_traded` (after the trade) → `hint_complete` (after the trade with no `hint_traded`, or before it when the player already holds every required item) → `hint`. Before a trade, an ally with no `hint` falls back to `"<name> has nothing to say."`; after one, with all three lines empty, `talk()` returns `""`.
- `Enemy.next_phase_factory` — **built.** `Callable[[], Enemy] | None`, default `None`. Triggers a seamless phase transition in `handle_enemy_defeat()` on this enemy's defeat. See "Multi-stage boss fights" below.
- `Enemy.next_wave_factories` — **built.** `list[Callable[[], Enemy]] | None`, default `None`. Spawns a set of ordinary adds on defeat instead of firing `next_phase_factory` immediately. See "Multi-stage boss fights" below.
- `Enemy.wave_gate_factory` — **built.** `Callable[[], Enemy] | None`, default `None`. Set on each add spawned by `next_wave_factories` (to that phase's own `next_phase_factory`) — never set directly by content, only by `handle_enemy_defeat()` itself. See "Multi-stage boss fights" below.
- `Player.dev_mode` — **built.** `bool`, default `False`. Whether developer commands are available for this save - lives on `Player`, not a `dev_tools.py` module global, so it's per-save state (round-tripped through `save_system.py` like any other field) rather than shared process-wide state. Set once via the "developer mode" name-trick or toggled via the mid-game `developer mode` command. See "Dev tooling" below.

## Testing conventions — follow these exactly, don't introduce new patterns
- **Plain `assert` statements only** — do NOT use `pytest.raises`. For testing that an exception is raised, use the manual pattern:
```python
  def test_example_raises_error():
      try:
          thing_that_should_fail()
          assert False, "Expected a ValueError but none was raised"
      except ValueError:
          pass
```
- **One test per behaviour**, not one test per method. Multiple `assert` lines in one test are fine if they're all checking the result of the *same* action — split into separate tests if you'd need "and" to describe what's being checked.
- **Test naming**: `test_<what>_<expected_behaviour>`.
- **Arrange-Act-Assert** structure in every test.
- **Identity vs equality**: classes in this project do NOT define `__eq__`. Test object presence with `is`/`in` against actual object references, never a freshly-constructed equivalent. Do not add `__eq__` to make tests easier.
- **Private attributes**: `Room` and `Inventory` use private lists (`_items`, `_enemies`, `_allies`, `_companions`) with controlled methods and a read-only `@property` for reading. Tests must go through public methods/properties, never `._items` etc. directly.
- Tests involving printed output use `capsys` — but note most methods that used to print now **return strings instead** (see below). Check whether `capsys` is actually still needed before using it.
- **Type-checking pattern**: `Room.get_exit()` and `Map.get_room()` return `Room | None`. Any test using the result must `assert result is not None` before accessing attributes, to satisfy Pylance's type narrowing.

## Design principles already established - don't fight these
- Composition over inheritance where the relationship is "has-a" (`Player.inventory`, `Player.skill_tree`), inheritance only for genuine "is-a" relationships.
- `Ally` is a standalone class, NOT `Ally(Character)`. Allies don't have combat stats. `Companion(Character)` is deliberately different — it **is** a `Character`, since it needs real combat stats to sit in `Player.team` and act via `choose_companion_action()`.
- Functions that coordinate two independent classes (moving an item between a `Room` and a `Player`, trading between an `Ally` and a `Player`) live as standalone functions, not methods. Functions that only touch one class's own state are methods on that class. Exception: `Inventory.use_item()` and `Inventory.unequip_item()` are methods on `Inventory` despite touching a `Character` too - this is established precedent, don't "fix" it to be a standalone function.
- **Per-ally behaviour is data, not branching.** Trade requirements (`Ally.required_items`), rewards (`Ally.reward`), and conditional dialogue (`Ally.hint`/`hint_complete`/`hint_traded`) live as attributes on the `Ally` object. Never write `if ally.name == "X"` in `engine.py` - if new per-ally behaviour is needed, add a new attribute to `Ally` instead. The same principle now extends to enemies' and companions' combat AI — see "Enemy AI and team combat" below.
- **No `Team` class for combat sides.** Per the "don't add classes for flexibility" rule below, the player's side and the enemies' side are both plain `list[Character]`/`list[Enemy]` — not a new abstraction. Player-side is `Player.team`, a property returning `[player]` or `[player, companion]` once a `Companion` is recruited and alive. See "Enemy AI and team combat" for the full reasoning.
- **Leading-underscore functions are module-internal helpers.** A function prefixed with `_` (e.g. `_score_candidate_actions`, `_best_attack_score`, `_greatest_threat_to_self`, `_candidate_attack_score`) is not meant to be imported/tested from outside its own module's test file.
- Don't add `__eq__`, extra attributes, or extra methods "for flexibility" unless something in the actual design already needs them.

## Enemy AI and team combat
The full system is **built**: team representation, round structure, target selection, `format_hp_line`'s generalization, the utility-scoring engine, all three actions (Attack, Defend/Brace, Heal) — and now the mirrored **Companion** side of all of the above. One scoring flaw was found in playtesting and the fix is decided and **now implemented** — see the end of this section.

- **Team representation**: no `Team` class (see "No `Team` class" above) — `player_team: list[Character]` (from `Player.team`) and `enemy_team` (i.e. `Room._enemies`, generally passed as `room.enemies`) are plain lists, threaded explicitly through every team-aware combat function.
- **Round order**: the player acts first (attack/item/etc.), then their companion (if any, alive) takes its own turn via `choose_companion_action()`, then every still-living member of `enemy_team` takes a turn via `choose_enemy_action()`, in list order. Combat stays locked until the whole `enemy_team` is defeated or the player flees. Every loop that runs enemy or companion turns stops rolling further actions once the player is dead — this was a real bug once (only one branch had the check).
- **`choose_enemy_action(enemy, player_team) -> str`** / **`choose_companion_action(companion, enemy_team) -> str`** are standalone functions in `combat.py`, not methods — per the existing rule that functions coordinating two independent classes' state live standalone. Return the name of the chosen action (`"attack"`, `"defend"`, or `"heal"`); callers branch on that string. Kept as **separate, mirrored functions rather than one shared function**, even though the underlying per-candidate math (`_best_attack_score()`, `_greatest_threat_to_self()`, `_candidate_attack_score()`) is fully reused by both.
- **AI model: utility-based scoring**, via `_score_candidate_actions()` / `_score_companion_candidate_actions()` (module-internal) and `choose_enemy_action()`/`choose_companion_action()`. Each returns a `dict[str, float]` of every candidate action's base score: `"attack"` (weighted by `aggression_weight` against the best available target — `_best_attack_score()`), `"defend"` (weighted by `caution_weight` against the greatest incoming threat — `_greatest_threat_to_self()` — excluded when `brace_amount == 0`), and `"heal"` (only included when `heal_amount > 0` — excluded entirely otherwise, not scored at zero). A random noise term is then added to every score (from `random.random()`, scaled by `randomness_weight` — not `random.uniform()`, to stay consistent with the monkeypatch-testable convention), then the highest-scoring action wins. This is the "lucky escape" mechanic.
- **Defend/Brace**: chosen action sets `pending_damage_reduction = brace_amount`, consumed by `take_damage()` on the next hit taken (see "Canonical attribute names"). `brace_amount` has no zero-exclusion rule (unlike Heal) — Defend is always a live candidate, even at `brace_amount = 0` (mechanically a no-op brace).
- **Heal**: restores `min(heal_amount, max_hp - hp)` HP (capped at `max_hp`, no overheal). `heal_amount = 0` excludes Heal from the candidate list entirely.
- **Personality is per-character data, not branching** — `aggression_weight`/`caution_weight`/`randomness_weight`/`brace_amount`/`heal_amount` (see "Canonical attribute names"), defaulting to a balanced, Defend/Heal-inert preset (`1.0`/`1.0`/`0.3`/`0`/`0`) so every existing `create_*()` call works unchanged. Tune specific enemies'/companions' actual values as part of "Populate all floors," not before.
- **`format_hp_line(player_team, enemy_team)`** is fully generalized to an N-combatant display on both sides, using `get_enemy_display_name()` for the enemy side.
- **`get_enemy_display_name(enemy, enemy_team) -> str`** appends a stable `(n)` index only when `enemy_team` genuinely has more than one enemy sharing that name — uniquely-named enemies display exactly as before. The index is computed from position among same-named enemies in the *full* `enemy_team` (dead included), so a survivor's number never shifts when a same-named teammate dies mid-fight.
- **`handle_target_command(command, enemy_team, player) -> str`** handles the player-facing `target <name>` / `target <name> <number>` command, setting `player.current_target` (persists across rounds; bare `attack` then hits it). **Important:** the optional trailing number always indexes the same full-team, same-named ordering that `get_enemy_display_name()` uses for its labels — not a separately-filtered living-only list. This was a real bug once; if this function is ever touched again, re-verify the number shown and the number that selects still agree, especially with a mix of dead/living same-named enemies.
- **`choose_enemy_target(enemy, player_team) -> Character`** / **`choose_companion_target(companion, enemy_team) -> Enemy`** pick who specifically gets attacked, once "attack" has already won as the chosen action. With only one living candidate, returns it directly with no scoring/randomness (preserves single-target `random.random()` call counts for every fight without a companion present). With two or more, scores each via `_candidate_attack_score()` plus independent noise.
- **Flee stays per-enemy**: every still-living enemy in `enemy_team` independently rolls its own parting-hit chance off its own HP% — `flee_combat(player, enemy_team)`.
- **Retreat/flee is explicitly player-only** — enemies never get it, full stop; not a candidate action, not planned as one. Companions don't flee either — they're dismissed instead (`dismiss_companion()`), not routed through `flee_combat()`.
- **A downed companion (`hp == 0`) is excluded from `Player.team` automatically** (see `Player.team`'s property definition) — enemies can never target something already downed, and `_best_attack_score()`/`_greatest_threat_to_self()` both filter to `is_alive()` first for the same reason (a team can go stale mid-round if a companion is downed by an earlier enemy's turn).
- **Deliberately extensible, not extended yet**: mana-based Spell-healing could become an additional candidate action in this same scoring function later. Light/Heavy/Ranged attack variety is **now built** (see "Weapon slots and attack variety" below) but only as a player-facing command choice - enemies/companions still only ever choose between attack/defend/heal, and their own attacks always default to `"light"`; giving AI its own attack-type choice would be a further extension of this same scoring function, not built. Spell attack variety was already covered by the existing `cast <spell>` command, so nothing further was needed there.

**Known issue, fix decided and now built — Defend no longer permanently dominates a losing enemy's/companion's choices.** Found in playtesting: the original formula (`caution_weight * self_missing_hp_ratio`) let Defend's score climb toward `caution_weight` as HP dropped regardless of any actual ongoing threat, with nothing pulling Attack back ahead — a low-HP enemy against a weak player would turtle for the rest of the fight. **Now implemented**: Defend's score is `caution_weight * self_kill_potential`, where `self_kill_potential = min(1.0, max(0, threat.attack_damage - self.armour) / self.hp)` maximised across the opposing team (`_greatest_threat_to_self()`) — this only spikes when the opponent could realistically finish the target off soon, so a weak attacker can never make a low-HP target panic-turtle. Shared by both `Enemy`'s and `Companion`'s scoring — genuinely symmetric, unlike the action-choosing functions themselves, which stay separate per the decision above.

## Content package layout
- **`content/` replaced the old single `content.py`.** `content/__init__.py` re-exports everything (`from .floor_N import *`, etc.), so `from dungeon_crawler.content import create_X` works exactly as before anywhere in the codebase, including every test - the split is invisible from outside the package. Because it's a star re-export, a new public function in any submodule is exported automatically; a leading-underscore one is not.
- **A factory lives in the module of the floor that uses it.** The moment a *second* floor needs it, it moves to `content/common.py` (currently only `create_small_healing_potion`). The rule runs both ways: once only one floor uses a factory, it moves back to that floor. `create_bronze_xiphos` went back to `floor_1.py` when the Minotaur's drop became the Labrys, and `create_aegis_fragment` was deleted once nothing used it. Narrative content used by exactly one floor stays in that floor's file even if it looks generic.
- **Cross-floor items are still just factory calls**: e.g. Hermes' required Skeleton Bone is created in `floor_1.py` (dropped there) but matched by name by Hermes' trade in `floor_2.py`.
- **`world_builder.py` holds `build_world()`**, kept out of `__init__.py` purely to avoid a name collision with `dungeon_crawler.world`. It wires the inter-floor `descend`/`ascend` exits and adds the dev test room.
- **Tests were not split**: `tests/test_content.py` still covers the whole package in one file.

## Armour slots and durability
- **Three independent slots.** `Armour.slot` (`"body"` default, `"helmet"`, or `"shield"`) decides which of `Character.equipped_helmet`/`equipped_body`/`equipped_shield` a piece occupies. `Armour.use()`/`unequip()` only ever swap the item currently in *that same slot* — all three coexist freely. **One cross-slot rule**: a shield can't be used with a two-handed (`"heavy"`-class) weapon - equipping either one unequips the other, whichever way round, rather than refusing.
- **`Character.armour` is calculated, not accumulated** - `base_armour` plus every worn, unbroken piece's `defence` (see "Canonical attribute names"). `use()`/`unequip()`/`take_damage()`/`repair_item()` never touch the number at all.
  - *(Two real bugs found and fixed by this: armour used to be a running total that each of those added to or subtracted from, and they disagreed about broken pieces. (1) `unequip()` subtracted a broken piece's `defence` a second time, `use()` added it back while still broken, and `repair_item()` re-added it even to an unequipped piece - with the new two-handed rule, equipping the Labrys over a broken Chipped Stone Aegis took armour to `-2`. (2) `serialise_player()` saved the total, worn gear included, then loading re-equipped that gear on top - every reload raised armour by the worn pieces' `defence`. Saves now store `base_armour`, with a fallback for older total-armour saves applied only after the gear is back on. All regression-tested in `test_items.py`/`test_exploration.py`/`test_save_system.py`.)*
- **Durability degrades on every hit taken, not just ones that connect.** `Character.take_damage()` decrements `durability` by 1 on every worn piece (helmet, body, *and* shield) unconditionally, after that hit's own damage (`reduced`) is already calculated — including a hit armour cut down to the `MINIMUM_DAMAGE` floor, and a `0`-damage hit. Only a dodge skips it, since a dodge returns before any of this runs.
- **The hit that breaks a piece still benefits from its own defence.** Because degradation happens *after* `reduced` is computed, a piece dropping from `durability == 1` to `0` on this exact hit doesn't retroactively increase this hit's damage — only the *next* hit loses the `defence` bonus (a piece at `durability == 0` stops counting towards `Character.armour`). The piece stays equipped when broken; it doesn't auto-unequip.
- **Repair, not replace.** `repair_item(item_name, player, room)` (`exploration.py`, routed via `repair <item>`) only works `if room.is_forge` (`Room.is_forge: bool = False`; only the Forge of Prometheus on floor 2 is one). Cost is `missing_durability * REPAIR_COST_PER_POINT` (`REPAIR_COST_PER_POINT = 2`) gold; a full-durability item returns "doesn't need repairing" without charging anything. On success, `durability` is restored to `max_durability`, and a piece that had broken counts towards `Character.armour` again automatically, if it's worn.
- **Slots and weights in real content**: two shields - the Wooden Shield (floor 0, light) and the Chipped Stone Aegis (Petrified Guardian's drop, floor 4, heavy, 3 DEF); one helmet - the Weathered Helm (Shade's drop, floor 1, light); every other piece is body armour - the Bronze Breastplate (medium), the Breastplate of Athena (light, 4 DEF) and Talos' Bronze Plating (heavy, 6 DEF, the best body armour). Athena's reward being *light* is deliberate: the best mid-game armour costs nothing in miss chance.
- **`max_durability` is no longer a flat `10` across every piece** — tuned per item after a playtesting pass found armour breaking (and staying broken, with no repair access past floor 2) well before a full dungeon crawl was over. Early pieces break *sooner* than the old default (Wooden Shield `6`, Weathered Helm `5`, Bronze Breastplate `8`), later ones last longer (Breastplate of Athena `15`, Chipped Stone Aegis `10`, Talos' Bronze Plating `18`) — cheap early gear is meant to be disposable, late-game gear durable.
- **Repair access was extended past floor 2 with three new one-way `"forge"` exits** (`world_builder.py`): Prayer Room (floor 3), Stony Lair and Maze of Pillars (floor 4) each connect directly to the Forge of Prometheus via a custom `forge` direction, hinted in the room's own description ("say 'forge' if you feel the pull toward it"). Routed through the same generic `elif command in current_room.exits:` movement branch as any other direction - no special-casing needed in `engine.py`.
- **The Forge also has reciprocal exits back out to each of those three rooms**, each locked until its one-way `forge` side has been used once - see "Fast-travel locks" below.

## Locked exits open for good
- **Walking through an item-locked exit unlocks it permanently.** `main()`'s movement branch calls `Room.unlock_exit(direction)` on every successful move (a no-op for an exit that was never locked), so a door that has been opened once never checks for its key again. `dev unlock`/`dev unlock all` go through the same method.
- **Saved**: `serialise_room()` stores `"locked_exits"` (the directions still locked), and `apply_room_data()` unlocks any direction the fresh `build_world()` locked but the save doesn't list. An older save with no `"locked_exits"` key leaves every lock in place. The older `unlocked_extras`/`locked_exits_removed` keys are still written, always empty, only so the save shape doesn't change.
- *(A real softlock found by `/balance-check` and fixed by this: the Wooden Sword and Wooden Shield are ordinary droppable items, and each is the only key to its own door. Dropping the sword inside the East room and walking out relocked the door with the only sword behind it - Chiron's trade needs the sword, and `descend` needs his coin, so floor 0 could never be left. Regression-tested with two `main()` smoke tests in `test_engine.py`.)*

## Fast-travel locks
- **`Room.fast_travel_locks: set[str]`/`Room.exit_activations: dict[str, tuple[Room, str]]`** (`world.py`) are a second gating mechanism, separate from `locked_exits` (item-gated): a direction in `fast_travel_locks` stays unusable until the *paired* exit (recorded in `exit_activations`, set via `register_fast_travel_activation()`) has been used from the other room first — e.g. the Forge of Prometheus's reciprocal `"prayer room"` exit only opens once the player has used Prayer Room's own `"forge"` exit at least once. `lock_fast_travel_exit()` marks a direction locked; `world_builder.py` wires all three Forge reciprocal exits (`"prayer room"`, `"stony lair"`, `"maze of pillars"`) this way, and `save_system.py` round-trips `fast_travel_locks` (`serialise_room()`/`apply_room_data()`), so an already-unlocked shortcut stays unlocked across a save/load.
- **Enforced directly in `main()`'s movement branch** (`engine.py`), checked ahead of `is_exit_locked()`'s item-gate check: if `command in current_room.fast_travel_locks`, the move is blocked with `"You haven't opened this shortcut yet - reach it from the other side first."` and nothing else happens. Otherwise, before the move itself, `current_room.exit_activations` is checked for this `command` - if present, the paired `(unlock_room, unlock_direction)` has `unlock_direction` discarded from `unlock_room.fast_travel_locks` (if it was still there) and `"The path back opens behind you."` is printed. Only then does `current_room = current_room.exits[command]` actually happen.
- **Real bug found and fixed here**: this enforcement didn't exist when the mechanism was first wired into `world_builder.py`/`save_system.py` - the data model and world-wiring were correct, but nothing ever read `fast_travel_locks` or called into `exit_activations`, so the Forge's reciprocal exits were unconditionally open from the start of the game regardless of whether the player had ever visited the paired room. Regression-tested in `test_engine.py`.

## Passive HP regeneration on movement
- **`PASSIVE_REGEN_PER_MOVE = 1`** (`engine.py`) - moving into a new room restores 1 HP if `player.hp` is below `int(player.max_hp * PASSIVE_REGEN_CAP_FRACTION)` (`PASSIVE_REGEN_CAP_FRACTION = 0.75`), printing `"You catch your breath as you move on. (+1 HP)"`. **The cap was added in a later balance pass**: uncapped, pacing back and forth between two cleared rooms healed the player to full for free, which made potions and attrition optional. It first went in at `0.5`, but combined with `MINIMUM_DAMAGE` that overcorrected - a careful floor 4 run reached nearly every fight at 7-12 HP and usually died at Medusa - so it was raised to `0.75`. Walking now tops you up to three-quarters of max HP; anything above that has to come from items. Added after a playtesting/balance pass found that with *zero* passive regen anywhere in the game (only `Consumable`/`StatusEffectItem` heals existed), a player who won every individual fight on a floor could still die partway through it from pure cumulative attrition. Exploration-only by construction - the check sits in the same movement branch as everything else in `main()`'s routing, which is never reached while `player.in_combat` (combat commands are dispatched first). A small mitigation, not a full fix - the real fix for the floor-3 attrition problem this was built for was adding more healing-potion drops, not this.

## Exploration conveniences - take all, equip, auto map, uncleared
- **`take all`** (`take_all()`, `exploration.py`) moves every item in the room into the inventory with one summary line (`"You take: A, B."`), and works mid-combat as a free action - see "Turn economy" below. **`take all from <ally>`** (`take_all_from_ally()`) does the same from an ally's own inventory (`"<ally> gives you: A, B."`), e.g. all three of the Wounded Soldier's gifts at once. Neither consumes or checks anything, so `QuestItem`s come along too.
- **`equip <item>`** - an explicit alternative to `use` for gear only; see "Turn economy" for how it validates and what it costs in combat.
- **`toggle auto map`** flips `Player.auto_map`; while on, `print_room()` appends `"Exits:"` plus `display_local_exits()` on every room entry.
- **`uncleared`** - `get_uncleared_rooms(all_floors, player)` lists, grouped under `"Floor N:"` headings in floor order, every visited room that still has something left, plus every *undiscovered* room within one step, or `"Every room you've visited has been cleared."` when there's neither. `get_uncleared_reasons(room)` supplies the reasons for a visited room, in this order:
  - `"enemies remain"` - any living, non-`respawns` enemy.
  - `"items left behind"` - anything still lying in `room.items`.
  - `"an unfinished trade"` - any ally for whom `has_unfinished_trade(ally)` is true: it has both `required_items` and a `reward`, and `trade_completed` is still `False`. Allies with nothing to trade (the Mentor, Prometheus, the Wounded Soldier) never count.
  - `"something here is worth a closer look"` - any unrevealed hidden exit, deliberately vague so it never names the direction.
- **`"undiscovered"`** - `get_undiscovered_rooms(all_floors, player)` returns every unvisited room one step through a *usable* exit of a visited room. It skips exits that are item-locked (without the item), guarded by a living enemy, or fast-travel-locked. Hidden exits aren't in `room.exits` until revealed, so they're never followed.
  - **Why only one step**: an adjacent room's name is already on screen via the map's exit list, so reporting it reveals nothing new. Going further would name rooms the player has never been shown.
  - **Undiscovered rooms on another floor** (e.g. Library of Athena, one `descend` below Styx Crossing) are grouped under that floor's own heading.
  - *(A real bug found and fixed here: the first version of `get_uncleared_reasons()` labelled any loose item in the room as `"an unfinished trade"`, while never detecting an ally's incomplete trade at all - a room with a dropped potion claimed a trade was open, and a room with a genuinely open trade looked cleared. Now split into `"items left behind"` and the real `has_unfinished_trade()` check. Regression-tested in `test_exploration.py`.)*
- **Also shown now**: `get_inventory_display()` appends each item's `details()` - every `Armour` piece on its own line with `(equipped)` then slot, weight, defence and `durability/max_durability`, never grouped into `x2` (two same-named pieces can differ in wear); weapons and other items still group. `stats` shows each attack type's miss chance, and `print_room()` shows every enemy's `[Armour N]`. Stat-skill descriptions end with their bonus (`"(+3 ATK)"`), and the ancestry list at character creation shows `INT` alongside ATK/DEF/HP.

## One-off contextual hints
- **`hints.py` holds every hint's text in one `HINTS: dict[str, str]`**, so wording is tuned in one place rather than scattered across trigger sites. `show_hint(player, key)` returns `"[Hint] <text>"` the first time a key is requested for that player (adding it to `Player.seen_hints`), and `""` on every later call - callers print the result only if it's non-empty. An unknown key raises `KeyError`, and `test_hints.py` pins the full key set.
- **Where each key fires** (eight keys, each shown at most once per save):
  - **In `print_room()`**, on every room entry and `look`:
    - `"combat"` - the room has a living, non-`respawns` enemy.
    - `"forge"` - `room.is_forge`.
    - `"practice_chamber"` - `room.is_practice_chamber`. The Practice Chamber's dummy respawns, so it never triggers `"combat"`.
  - **In `main()`**:
    - `"skill_points"` - checked before every command prompt while `skill_tree.skill_points > 0`.
    - `"guarded_exit"` - right after a guarded exit refuses a move.
    - `"forge_shortcut"` - right after a Forge reciprocal exit unlocks (`"The path back opens behind you."`).
    - `"passive_regen"` - right after the first passive regen tick.
    - `"autosave"` - right after the first autosave.
- **Hard-coded numbers in hint text go stale silently.** `"passive_regen"` says "three quarters", matching `PASSIVE_REGEN_CAP_FRACTION = 0.75`. `test_hints.py` fails if the constant changes, so the wording gets updated alongside it.

## Minimum damage
- **`MINIMUM_DAMAGE = 1`** (`characters.py`) - in `Character.take_damage()`, any hit with `amount > 0` that isn't dodged deals at least 1, however much brace (`pending_damage_reduction`), armour, and Iron Hide would otherwise absorb. Applied after all three reductions, before durability/Last Stand/Thorns. An attacker with `0` attack (the Training Dummy) still deals `0`, and a dodge still returns `0` before any of this runs.
- **Why**: armour is a flat subtraction, so once `armour >= enemy.attack_damage` the enemy did literally nothing. A pure-Defence build became invulnerable to every enemy in the game, and the Medusa rebalance (see "Multi-stage boss fights") was fighting the same cliff. The floor removes the cliff everywhere at once, rather than being retuned enemy by enemy.
- **Knock-on effect**: Thorns now always has something to reflect, since no landed hit is ever fully blocked. Its own `max(1, reduced // 4)` minimum is unchanged.

## Guarded exits
- **A third exit-gating mechanism**, alongside `locked_exits` (item-gated) and `fast_travel_locks` (use-the-other-side-first). A direction in `Room.guarded_exits` (set via `Room.guard_exit(direction)`, `world.py`) can't be used while any living, non-`respawns` enemy remains in that room.
- **`get_exit_guardian(room, direction) -> Enemy | None`** (`exploration.py`) returns the first such enemy, or `None` if the exit isn't guarded or nobody's left to guard it.
- **Checked in `main()`'s movement branch after the fast-travel-lock and item-lock checks**, blocking with `"<name> bars the way - you'll have to deal with it first."`.
- **Guarded in real content**:
  - **In `build_floor_4()`**: Labyrinth of the Minotaur's `south` (the Minotaur) and Maze of Pillars' `south` (Talos).
  - **In `world_builder.py`**: Overgrown Forest's `descend` (the Centaur, floor 3's last fight) and Lair of Medusa's `descend` (the whole Medusa chain). The chain never opens the exit early, because `handle_enemy_defeat()` spawns each wave/next phase in the same defeat handling that removes the previous one.
  - **The Labyrinth's west/east/`ascend` stay open**, so the player can still retreat or clear the side rooms first.
- **No bypass through the Forge**: Stony Lair's `forge` exit leads to the Forge, but the Forge's reciprocal `maze of pillars` exit stays fast-travel-locked until Maze of Pillars' own `forge` exit has been used, which means reaching Maze of Pillars first.
- **Why**: before this, combat only started on `attack`, and movement never checked for living enemies - every fight in the game could simply be walked past, including the Minotaur, which is meant to be a hard skill-point gate. Guarding just the critical-path exits enforces that without changing anything about how combat starts.
- **The Minotaur gate was retuned once more (`hp` 25 → 28, `armour` 2 → 3).** A later `/balance-check` found that a zero-skill player who skipped the side rooms, but paced to the 75% regen cap first and carried the three critical-path potions (Wounded Soldier, Crypt Keeper, Lurker), beat him 100% of the time with light attacks - potions are free actions, so they stack straight onto effective HP. The retune takes that to 0%, and heavy-attack gambling from about half to about a fifth, while players who did the side content still win every time with light attacks. The same pass raised the Centaur (`14/5` → `18/6`, so floor 3's exit guard is no easier than the Lurker before it) and raised the Satyr, Lamia and Ember Wraith's HP. The first raise (+5 each) still left two-hit fights, since the player hits for 16-20 by then, so a follow-up audit took them to `26`/`30`/`28` (originally `15`/`20`/`19`). For a balanced build these fights now last about 3.6 turns rather than 2.3, and cost about twice the HP; an all-Attack build still two-shots them, which is its trade-off.
- **Static, not saved** (same category as `exit_activations`) - the live "is it still guarded" state comes from `room.enemies`, which already round-trips through `save_system.py`. `dev kill`/`dev clear room` both clear a guard, since they empty the room of living enemies.
- **Shown when listing exits**: `display_local_exits()`/`display_map()` label a guarded exit `"<direction> -> <room> (guarded by <name>)"`, and `display_map()` doesn't map past it. An unopened fast-travel shortcut shows as `"Sealed Shortcut"` the same way. *(Known cosmetic gap: `display_map()`'s "Sealed Shortcut" lines are missing the two-space indent every other exit line has.)*

## Skill tree tiers
- **Attack and Defence paths have five tiers each, bonuses `2/3/4/5/6`** (`SkillTree.__init__`):
  - **Attack**: Iron Grip, Honed Instinct, Warrior's Fury, Spartan Discipline, Blessing of Ares.
  - **Defence**: Hardened Skin, Steady Stance, Aegis Ward, Tempered Bronze, Bronze Resolve.
  - **Abilities** is unchanged at four (Twin Strike, Retribution, Last Stand, Nimble Grace at `0.35` dodge).
- **Previously three tiers at `2/4/6`.** The new curve is gentler early (+5 at two points instead of +6), but a maxed path is now +20 instead of +12 - part of why `MINIMUM_DAMAGE` matters more, not less, with these tiers.

## Weapon slots and attack variety
- **Two independent slots, not one - mirrors Armour's helmet/body split.** `Weapon.slot` (`"melee"` default, `"ranged"` the other option) decides which of `Character.equipped_melee_weapon`/`equipped_ranged_weapon` a piece occupies. `Weapon.use()`/`unequip()` only ever swap the item currently in *that same slot* - a melee weapon and a ranged weapon coexist freely.
- **Weapon damage is read at attack time, not accumulated on `attack_damage`.** Equipping/unequipping a `Weapon` never touches `Character.attack_damage` at all (a deliberate departure from the old design; `Armour` has since stopped keeping a running total too - see "Armour slots and durability") - `Character.attack()` reads `weapon.damage` directly off whichever slot matches `attack_type` and adds it in for that hit only.
- **`Character.attack(target, attack_type="light")`** - `attack_type` is `"light"`, `"heavy"`, or `"ranged"`. `"light"` and `"ranged"` draw from `equipped_melee_weapon`/`equipped_ranged_weapon` respectively, with identical maths otherwise (no multiplier, and a miss only through armour weight - see the next section). `"heavy"` always draws from `equipped_melee_weapon`, multiplies the total by `HEAVY_ATTACK_MULTIPLIER` (`1.75`), but has a `HEAVY_ATTACK_MISS_CHANCE` (`0.4`, raised from `0.3` in a balance pass - at `0.3` a heavy attack out-damaged a light one on average for every build, so it was a free upgrade rather than a gamble) chance to miss entirely (0 damage, turn still spent) - **decided heavy attack trade-off: a chance to miss, not a separate stamina resource** (see roadmap.md). Double Strike's second hit always uses the un-multiplied `base_damage // 2` regardless of `attack_type`, and **ignores the target's armour** (`take_damage(..., ignore_armour=True)`) - only the first hit is ever boosted by the heavy multiplier or Bull Rush. The armour bypass was added because at `base_damage // 2`, the second hit mostly bounced off any armoured enemy, making Twin Strike a trap as the Abilities path's first pick.
- **`handle_combat_command()`'s `attack` branch** (`combat.py`) parses an optional trailing type (`attack`, `attack light`, `attack heavy`, `attack ranged`) - an unrecognised type returns an error message without attacking, and `attack ranged` with no `equipped_ranged_weapon` returns `"You have nothing to shoot with - equip a ranged weapon first."` without attacking either. `resolve_combat_round()`/`resolve_attack_and_check_defeat()` both take `attack_type` as an optional parameter (default `"light"`), threading it straight through to `player.attack()`.
- **Enemies and companions never use heavy/ranged** - see "Enemy AI and team combat" above. Attack-type variety is player-only for now.
- **One real ranged `Weapon` exists** (`weapon_class="ranged"`) - the Harpy-fletched Bow (`create_harpy_fletched_bow()`, `content/floor_3.py`, `slot="ranged"`, 4 damage), dropped by the Harpy in Cave of Harpies (floor 3), so `attack ranged` is reachable through normal play (and via `dev add harpy-fletched bow`). Every other `Weapon` in `content/` defaults to `"melee"`, and there's no dev-test ranged weapon.

## Weapon classes, armour weight, and miss chance
- **Every attack can now miss, not just heavy ones.** `Character.get_miss_chance(attack_type)` is rolled first in `attack()`:
  - **Light and ranged**: only `armour_weight_penalty()` - the sum of `ARMOUR_WEIGHT_MISS_PENALTY` (`light 0.0`, `medium 0.05`, `heavy 0.10`) over every worn piece, broken ones included (they're still being worn). An unarmoured, or all-light, attacker makes no miss roll at all, so no `random.random()` call is spent on it.
  - **Heavy**: `HEAVY_ATTACK_MISS_CHANCE` (`0.4`), plus `BLADE_HEAVY_MISS_MODIFIER` (`-0.1`) with a blade, plus the armour penalty - and *then* halved by Reckless Strength.
  - Clamped to `0`-`MAX_MISS_CHANCE` (`0.95`), though no current combination reaches either end. Spells never call it. Enemies and companions never wear armour or equip weapons, so they never miss.
- **Weapon classes** (`Weapon.weapon_class`):
  - **`blade`** - the default; lowers the heavy miss chance. The Wooden Sword, Bronze Xiphos, Sun-scorched Dagger (5) and Serpent's Kiss (6).
  - **`heavy`** - two-handed; a heavy attack uses `HEAVY_WEAPON_MULTIPLIER` (`2.0`) instead of `1.75`. The Labrys (7).
  - **`piercing`** - carries `armour_pierce`, subtracted from the target's armour. The Spear of Ares (6, pierce 2) and Lamia's Fang (4, pierce 2).
  - **`ranged`** - the ranged slot. The Harpy-fletched Bow (4).
- **Signature properties for unique drops**, each read off the weapon actually used for this attack (a lifesteal bow does nothing for a melee hit). The follow-up order inside `attack()` matters:
  - **Lifesteal** (Lamia's Fang) heals half the damage dealt, capped at `WEAPON_LIFESTEAL_CAP` (`3`) per hit. **Why the cap**: the heal scales with the player's *total* damage, not the weapon's, so at about 16 damage per hit the uncapped Fang healed about 8 HP a turn - more than any floor 4 enemy dealt back - and careful players finished the Medusa chain near full HP. With the cap, three-quarters of heals hit it, and the lowest HP reached at Talos without pacing drops from about 13.5 to 10, with survival unchanged. Innate lifesteal (`Character.has_lifesteal`) is uncapped, and never stacks with a weapon's - see "Canonical attribute names".
  - **Cleave** (the Labrys), heavy attacks only - `_cleave()` hits the first *other* living, non-`respawns` combatant in `attack()`'s new `others` parameter for half the swing's damage (the multiplied hit, before Bull Rush's +3), whether or not the main target died. `resolve_combat_round()` passes `enemy_team` as `others`; `resolve_pending_defeats()` then processes a cleave kill like any other.
  - **Then only if the target survived**: Petrifying Gaze (15%) and the weapon's `poison_chance` (Serpent's Kiss, 15%, `WEAPON_POISON_AMOUNT`/`WEAPON_POISON_DURATION` = `-3`/`3`) roll separately - both landing prolongs one Poison - then Double Strike's second hit.
- **Shown to the player**: `stats` has a `Miss chance: N% light / N% heavy / N% ranged` line, the inventory shows each item's `details()`, and `print_room()` shows every enemy's `[Armour N]`, so piercing and weapon choice can be judged before a fight.
- **Why**: after the ancestry rebalance, weapon choice was just "highest damage number wins", and two of floor 4's five weapon drops were never upgrades. Classes make each drop a different trade-off (reliability, burst, piercing, shield compatibility) rather than a strict ladder.

## Turn economy: free vs turn-ending actions
- **`Item.ends_turn(character) -> bool`** (default `True`) decides whether using an item mid-combat consumes the player's turn (triggering the companion's/enemy's turn) or is a free action. `Consumable.ends_turn()` overrides it to `heal_amount <= 0` - a genuine heal is free. `StatusEffectItem.ends_turn()` overrides it to `self.amount < 0` - a self-targeted heal-over-time is free, an offensive (negative-`amount`) one still ends the turn. `Reviver.ends_turn()` always returns `True` - reviving a downed companion is a significant action, not a quick self-heal, even though its `heal_amount` is positive. Casting a spell (`cast <spell>`) always ends the turn - there's no free-action branch for spells.
- **Picking things up mid-combat is free.** `take <item>` and `take all` are valid combat commands (`handle_combat_command()`), and neither ticks status effects nor ends the turn - they don't touch `turn_started` at all. This is what makes loot dropped partway through a multi-enemy fight usable before it ends: the Gorgons' potions during the Medusa chain were previously stranded on the floor, since loot always lands in the room and `take` wasn't a combat command. `take <item> from <ally>` is still refused mid-combat.
- **`equip <item>` ends the turn like `use` does**, because it *is* `use` once validated. `check_equippable()` (`exploration.py`) runs first and refuses a missing item, a non-`Weapon`/`Armour` item, or one already equipped - so `equip` can never drink a potion, and a refused `equip` costs no turn. Outside combat, `equip` goes through the same check and then `Inventory.use_item()`.
- **`Character.turn_started: bool`** (default `False`) guards `tick_start_of_turn_if_needed()` (`combat.py`) against ticking status effects/spell cooldowns more than once in a single round - a free action followed by a turn-ending one in the same round must only tick once. `resolve_companion_and_enemy_turns()` (called whenever a round actually ends) resets it back to `False` for the next round - every turn-ending branch in `handle_combat_command()` relies on that shared reset, not on resetting it itself.
- **Real bug found and fixed**: `turn_started` was never actually being set to `True` anywhere, so the double-tick guard above was a no-op - a free heal followed by an `attack` in the same round would tick Poison (and decrement spell cooldowns) twice for one real turn. Fixed by setting `player.turn_started = True` inside `tick_start_of_turn_if_needed()` itself, immediately after the "already ticked this round" check. Regression-tested in `test_combat.py`.

## Defeat handling - resolve_pending_defeats()
- **One function processes every defeat, whatever caused it.** `resolve_pending_defeats(player, room)` (`combat.py`) handles every enemy still in `room.enemies` at 0 HP via `handle_enemy_defeat()`, then decides whether combat continues. It needs no before/after snapshot: `handle_enemy_defeat()` always either removes a dead enemy or resets a `respawns` one to full HP, so any enemy still in the room at 0 HP is by definition unprocessed. It's therefore correct for any kind of kill - an attack, a spell, a companion, a poison tick, or Thorns.
- **Where it runs**: at the end of `resolve_attack_and_check_defeat()`, and at the end of `handle_combat_command()`'s `cast` and `use` branches (after their HP line). Every turn-ending action that can kill something ends with it.
- **Afterwards**: `player.in_combat` is `True` only if a living, non-`respawns` enemy remains.
  - **If none remains**, `current_target` is cleared.
  - **Otherwise the current target is kept if it's still alive** - including a boss phase or wave add that `handle_enemy_defeat()` just targeted - and moves to the first survivor if not.
- **Real bug found and fixed**: the defeat loop used to live only inside `resolve_attack_and_check_defeat()`, and only looked at enemies alive *before* the attack. The `cast` and `use` branches never processed defeats at all. A spell kill, or an enemy dying to a poison vial's tick on its own turn, left the enemy in the room at 0 HP - no loot, no XP, no gold, and combat never ended, so exploration commands stayed refused as "mid-combat". `resolve_pending_defeats()` also cleans up any enemy a save captured stuck at 0 HP by that bug. Regression-tested in `test_combat.py` (a spell kill and a poison kill) and `test_engine.py` (`look` works straight after a spell kill); all three fail against the old `combat.py`.

## Companion duels and levelling
- **A companion can insist on a duel before joining** (`Companion.duel_enemy_factory`). While `requires_duel` is true, `recruit` refuses with a pointer to `challenge <name>`, and `print_room()` says `"<name> is here."` rather than `"could be recruited here"`.
- **`start_duel(name, room, player)`** (`exploration.py`, routed via `challenge <name>` outside combat) swaps the companion out of the room for the `Enemy` its factory builds, tagging that combat form with `duel_companion` and `duel_return_hp` (the player's HP right now), and starts combat. It refuses a missing companion, one with no duel, and one already beaten.
- **The duel is non-lethal on every path**:
  - **Win** - `handle_enemy_defeat()` returns the companion to the room with `duel_won = True`, shows `duel_won_message`, runs the combat form's `defeat_effect`, and restores the player's HP. **No XP, gold or loot**, whatever the combat form carries, so a duel can't be farmed.
  - **Loss** - `protect_duel_loser()` runs first inside `resolve_pending_defeats()`: if the player is at 0 HP mid-duel, it sets HP to 1 (so nothing downstream ever sees a death), then ends the duel with `duel_lost_message` via `end_duel()`, which puts the companion back un-won and restores the pre-duel HP. Since every turn-ending combat branch ends in `resolve_pending_defeats()`, this covers attack, cast, use and poison ticks alike.
  - **Both fall on the same turn** - `protect_duel_loser()` leaves it to the defeat sweep, which counts it as a win.
  - **Flee** - `handle_combat_command()`'s `flee` branch calls `end_duel()` too (`"<name> lets you go, unimpressed."`), restoring HP even after a parting hit.
  - A duel can never be saved mid-fight, since `save` is refused in combat - so the combat form never needs rebuilding from a save.
- **The combat form is deliberately not in `ENEMY_REGISTRY`.** It shares the companion's name, so registering it made `dev spawn shade of achilles` spawn an unlinked, lethal duellist instead of the companion. It only ever exists via `start_duel()`.
- **Companions level up alongside the player**: every enemy's `experience_reward` goes to `player.companion` too (downed or not). `Companion.gain_experience()` keeps levelling while the XP covers the next threshold (unlike `Player.gain_experience()`, which levels at most once per call). A level-up raises current HP only if the companion is standing, so levelling can never revive a downed one.
- **Saved as level and XP, never stats** (`serialise_companion()`/`companion_from_save_data()`, `save_system.py`): on load, `restore_level()` replays each level-up on a fresh companion, so stats can't drift from the level - the same lesson as the armour double-counting bug. Also saved: HP (clamped to the restored `max_hp`), `duel_won`, active effects, and `home_room` **by name**, re-linked to the loaded world's real room. Rooms save their companions too (`serialise_room()`'s `"companions"`), so a won duel, or a recruited companion's absence from their camp, survives a reload. Older saves missing any of these fall back to a fresh companion's values.
  - *(Four real bugs caught in review before this shipped, each now regression-tested: `serialise_companion()` stored the `Room` object itself, so every save crashed - the floor 5 camp always holds a companion; `companion_from_save_data()` never returned the companion, so loading deleted Achilles from his camp; `restore_level()` referenced `_level_up` without calling it; and `challenge` stripped the prefix string instead of the name, so it never matched anyone.)*
- **The Shade of Achilles** (`create_shade_of_achilles()`, `content/floor_5.py`, Shadow of Army Camp) is the first real recruitable `Companion`: 30 HP / 8 attack / 2 armour, `aggression_weight=1.5`. His duel form (`create_shade_of_achilles_duellist()`) is tougher - 40 HP / 10 attack / 3 armour, `brace_amount=3`, `dodge_chance=0.15` - since losing costs nothing and it can be retried. Beating it grants a skill point via `defeat_effect`.

## Practice Chamber and respawning enemies
- **Real, in-game content, not dev-only** - a "Practice Chamber" room on floor 2 (`build_floor_2()`, `content/floor_2.py`), connected east/west to the Forge of Prometheus. Floor 2 has six rooms now, not five.
- **`Enemy.respawns: bool`** (default `False`) - the room's dummy (`create_practice_dummy()`) is the only enemy with it set so far. `handle_enemy_defeat()` (`combat.py`) special-cases it: instead of `room.remove_enemy()` plus loot/XP/gold, it resets `hp` to `max_hp`, clears `active_effects` and `pending_damage_reduction`, and returns a `"<name> resets, ready for another round."` message - no rewards are granted, regardless of what `gold_reward`/`experience_reward` are set to.
- **`resolve_pending_defeats()`'s survivor check** excludes every `respawns` enemy from the "is combat still going" decision. This matters because `handle_enemy_defeat()` just made the respawning enemy alive again (full `hp`) - without the exclusion, a solo practice dummy would never let combat actually end.
- **Free spellcasting only, not free items/weapons.** `handle_combat_command()`'s `cast` branch skips the cooldown/mana checks *and* skips deducting mana/setting a cooldown whenever `room.is_practice_chamber` is `True` - casting is genuinely free while inside. This doesn't touch `Item.ends_turn()` or anything in "Turn economy" above - a spell cast here still ends the turn exactly as it does everywhere else, it just doesn't cost mana or start a cooldown. Item/weapon use was already free of any resource cost (only `ends_turn()` governs those), so nothing needed to change for them.
- **`dev_tools.py`'s `_apply_stat(character, attr_name, value, prefix, display_name)`** is the generic reflection/`STAT_ALIASES` logic factored out of `handle_dev_set()`, shared with the new **`handle_dummy_set(stat_name, value_str, dummy)`** - same hp/max_hp consistency behaviour, but message-prefixed `[Practice]` (not `[DEV]`) and with no `skillpoints` special case (`Enemy` has no `skill_tree`).
- **`dummy set <stat> <value>`** (`main()`, `engine.py`) is a normal player command, checked in the main routing regardless of `player.dev_mode` - it finds the current room's `respawns` enemy (`next((e for e in current_room.enemies if e.respawns), None)`), erroring with `"There's no practice dummy here."` if none is present. Listed in `get_controls_text()`/the README's Controls section like any other real command - unlike every `dev ...` command, which is deliberately absent from both (see `dev_guide.md`'s own opening note).

- **Planned, not built: a drop chance on respawning enemies** (roadmap.md's "Drop chance on respawning enemies"). Right now the respawn branch of `handle_enemy_defeat()` returns before any loot/XP/gold code runs, so a `respawns` enemy can never reward anything. The plan is a per-enemy chance, rolled with `random.random()`, of dropping loot on each "defeat". **The catch to solve first**: `Enemy.loot` holds item *instances*, so a repeatable drop needs a fresh item each time - most likely factories, like `next_phase_factory`. **Probably not for this room's dummy**: the Practice Chamber is meant to be reward-free (its one-off hint says the dummy "gives no rewards"), so the drop chance is aimed at future respawning content instead.
- **Planned, not built: trial mode** (roadmap.md's "Trial mode"). A set number of rounds, each harder than the last, played inside the normal game world, and genuinely beatable - the finite, rewarding counterpart to this room's endless dummy. It will eventually award an achievement once achievements exist. **Reuse, don't rebuild**: the wave mechanic (`next_wave_factories`/`wave_gate_factory`) already does "clear these, then the next thing appears", and round scaling should share the planned difficulty system's stat multiplier. Still undecided: where it lives, what scales between rounds, whether dying there is a real death, retries, and rewards.

## Status effects and spellcasting
- **`StatusEffect(name, amount, duration)`** (`status_effects.py`) is the one shape for poison, flame, and heal-over-time alike — `amount < 0` deals `min(-amount, character.hp)` damage per tick, `amount >= 0` heals `min(amount, character.max_hp - character.hp)` per tick (capped, no overheal); `tick(character)` applies one tick and decrements `duration` by 1.
- **Stacking rule, decided and shared with Spells**: reapplying an effect with the same `name` **prolongs its `duration`** (durations add) rather than stacking a second simultaneous instance or simply replacing it. `Character.apply_status_effect()` never changes `amount` on reapplication, only `duration`.
- **`Character.tick_status_effects()`** ticks every active effect in order, removing any whose `duration` reaches `<= 0` after that tick, and **stops ticking further effects the instant a tick kills the character** — the exact same "stop once dead" precedent as `resolve_combat_round()`'s own turn loop — appending the death message when that happens.
- **`StatusEffectItem(Consumable)`** (`items.py`): a non-negative `amount` applies to the user themselves; a negative `amount` applies to `player.current_target`, reusing the existing `target <enemy>` command as the aiming mechanism rather than a new `use <item> on <target>` syntax (decided in roadmap.md).
- **`Spell(name, description, mana_cost, damage=0, heal_amount=0, effect_name=None, effect_amount=0, effect_duration=0)`** (`spells.py`): damage, heal, and status-effect components are all optional and freely combinable in one spell (a "combo" spell can deal damage *and* apply poison in a single cast). `damage > 0` and a negative `effect_amount` both require a target; a pure heal or a positive (self) `effect_amount` never does.
- **Resource model, as built**: a flat mana pool (`Player.mana`/`max_mana`, both default `20`) plus a flat, uniform 1-turn cooldown per spell (`Player.spell_cooldowns[spell.name] = 1` on every successful cast — not yet varied per spell). Mana recovers only via the `rest`/`wait` command (`engine.py`, exploration-only, `REST_MANA_AMOUNT = 10` per use) — no passive per-turn regen.
- **`cast <spell>`** (`handle_combat_command()`) validates, in order: the spell is known, it isn't on cooldown, there's enough mana — then `Spell.would_fail(caster, target)`. Only after all of that does it tick, then cast, then deduct mana and set the cooldown.
- **The `would_fail()` guard pattern, built specifically to preserve "a failed action costs nothing"**: `Spell.would_fail(caster, target)` and `Item.would_fail(character)` (default no-op on the base `Item` class) mirror the exact condition their real `cast()`/`use()` would raise on, or would be wasted on, *without* mutating anything. Four `Item` subclasses override it:
  - **`StatusEffectItem`**: an offensive one with no living target.
  - **`SpellBook`**: the spell is already known.
  - **`Consumable`**: a genuine heal (`heal_amount > 0`) at full HP, *"would be wasted"*. The `heal_amount > 0` guard matters because `SkillPointReward` inherits it with `heal_amount = 0` and must never be blocked.
  - **`Reviver`**: no companion, or one that isn't downed.

  **Deliberately not blocked at full HP: a heal-over-time `StatusEffectItem`** (positive `amount`). Drinking a regen tonic right before a fight is a legitimate pre-buff tactic, unlike wasting an instant heal - `StatusEffectItem.would_fail()` has no full-HP check, and `test_items.py`/`test_combat.py` lock that in.
  - **`Inventory.use_item()` checks `would_fail()` itself too** (raising its message as a `ValueError` before `use()` runs), so the rule holds outside combat as well - a Reviver with no downed companion, or a potion at full HP, stays in the inventory instead of being consumed for nothing. *(A real bug fixed here: before this, a Reviver used with no downed companion still reached `use()`, printed its "nothing to revive" message, and was then removed as a `Consumable`.)* `handle_combat_command()`'s `cast`/`use` branches call `would_fail()` **before** ticking status effects/cooldowns, so a doomed action never costs the player a tick of their own pre-existing state — only *after* that check passes does ticking (of pre-existing state only) happen, followed by the actual `cast()`/`use_item()` call, which `would_fail()` has already guaranteed can't raise.
  - *(A real bug found and fixed here: ticking originally ran **after** the action instead of before it, so a freshly-cast spell's own brand-new cooldown/effect got immediately consumed by that same tick, in the same turn it was created — a spell's cooldown silently never blocked a repeat cast, and a self-cast heal-over-time got its first tick "for free" the instant it landed, before the caller could ever observe the untouched, freshly-applied state. Fixed by reordering to validate fully → tick pre-existing state → commit the new action, so "this turn's" tick can only ever touch state that already existed before this turn.)*
  - **`"use "`'s pre-check is slightly more involved than `"cast "`'s**: since "item not found by name" is by far the most common `use` failure and must stay free regardless, `handle_combat_command()` looks the item up by name *before* calling `would_fail()` on it (mirroring `Inventory.use_item()`'s own lookup and its exact `"No item named '...' in inventory."` message) — only a *found* item's own `would_fail()` sits behind the tick.
- **A target-applied effect (e.g. poison cast on an enemy) legitimately ticks the same round it's applied** — this is *not* a bug, unlike the self-applied case above. The enemy's tick happens as part of *its own turn* within `resolve_companion_and_enemy_turns()`, which genuinely runs later in the same round, after the player's cast — exactly matching the established round order (player, then companion, then each enemy). Don't "fix" this if it's ever queried again.
- **Not yet built**: enemies/companions never cast spells or apply status effects — `choose_enemy_action()`/`choose_companion_action()` still only ever choose between attack/defend/heal. Spellcasting AI would be a future extension of the existing utility-scoring system, same shape as Defend/Heal joining originally, not a redesign.

## Dev tooling (engine.py, gated by player.dev_mode / "developer mode")
Everything in this section requires `player.dev_mode`, **except** `dummy set <stat> <value>` (routed separately in `main()`, not through `handle_dev_command()` at all) - see "Practice Chamber and respawning enemies" above.
- **`player.dev_mode`, migrated off a `dev_tools.py` module global (`DEV_MODE`).** The old module-level flag was shared process-wide state - it wouldn't persist across a save/load (every reload of `main()` reset it), and two separate `Player`s in the same process (e.g. across tests) could leak state into each other unless explicitly reset. `Player.dev_mode` fixes both: it's a normal instance attribute, set once via the "developer mode" name-trick or toggled via the mid-game `developer mode` command (`player.dev_mode = not player.dev_mode`), and now round-trips through `save_system.py` like any other field - see "Save/load system and the title screen" above. `main()`'s routing reads `player.dev_mode` directly wherever it used to read `dev_tools.DEV_MODE`.
- `dev set <stat> <value>` is a **single generic command**, not one branch per stat — it reads/writes any real `Player` attribute name (via a small `STAT_ALIASES` dict for shorthand like `atk`/`def`, then `setattr`). New stats (e.g. Intellect) work automatically the moment the attribute exists on `Player` — never add a new hardcoded `dev set` branch for a new stat.
- Three distinct removal scopes, don't conflate them: `dev remove <character>` (one matching instance), `dev remove all <character>` (every instance of that one name), `dev clear room` (everything, regardless of name). None of the three trigger `handle_enemy_defeat()` or loot — a dev removal is not a kill.

Every branch must return the tuple shape, including `None` for the room when not teleporting — a bare string return here was a real bug once (`dev spawn` printed the raw tuple because a stale call site hadn't been updated after this return type changed).
- Dev commands are checked **before** the `in_combat` branch in `main()`'s routing, not inside the exploration-only path — they must always work regardless of combat state. This was a real bug, now fixed; don't reintroduce it by nesting the `dev ` check inside another branch.
- Maintenance: every new enemy/ally `create_*()` function needs a matching line in `ENEMY_REGISTRY`/`ALLY_REGISTRY` (mirroring `ITEM_REGISTRY`), so `dev spawn` can find it.
- **Closed**: `dev spawn` now supports `Companion` via `find_companion_by_name()`/`COMPANION_REGISTRY`, `dev grant spell` supports `Spell` via `find_spell_by_name()`/`SPELL_REGISTRY`, and `ITEM_REGISTRY` has entries for a `SpellBook` and both signs of `StatusEffectItem` — all backed by dev-only test content in `content/dev_content.py` (`create_test_companion`, `create_test_spell`, `create_test_spellbook`, `create_test_healing_tonic`, `create_test_venom_vial`), not real narrative content. `ENEMY_REGISTRY` also has a `"test boss"` entry (`create_test_boss`) exercising the full multi-stage boss chain (phase transition + wave gating) - see "Multi-stage boss fights" above. ## A known gap in /move-tests — check for this every time
`/move-tests` fixes imports in the *new* file it creates, but does NOT clean up the *old* file's import line for names that just left. After every `/move-tests` run, manually check the source file's own top-level import statement (e.g. `test_engine.py`'s `from dungeon_crawler.engine import ...` line) and remove any names that no longer live there — otherwise the file fails to import at all with a confusing `ImportError`, even though the actual moved tests are fine. This will happen again on every subsequent `/move-tests` run.

## Ancestry / character creation system
- `content/ancestries.py` holds `ANCESTRIES: dict[str, dict]` (re-exported from `content`) - each entry has `label`, `attack`, `armour`, `hp`, `intellect`, `bonus_skill_point`, `secondary_effect`, `secondary_ability_label`.
- Stats are **set outright**, not added to a baseline. Picking an ancestry replaces the player's starting stats entirely.
- `character_creation.py`'s `choose_ancestry()`, `choose_secondary_ancestry()`, and `create_player()` handle selection and construction, called in `main()` before the world is built. `main()`'s order is `choose_ancestry()` → `choose_secondary_ancestry(ancestry_key)` → `create_player(name, ancestry_key, secondary_ancestry_key)`.
- If adding a new ancestry: keep its total "power budget" roughly proportional to existing entries (no strict upgrades over `"basic"` in every stat at once) - see the existing table for the balance pattern (offence-leaning options sacrifice defence, defence-leaning options sacrifice offence, HP-heavy options sacrifice both). A new entry also needs a `secondary_effect` (a `lambda player: setattr(player, "has_...", True)`, or `None` for a stat-only pick) and a `secondary_ability_label` describing it - see "Secondary ancestry abilities" below.
- **The whole table was rebalanced once, driven by a fight-by-fight simulation of floors 0-4** (primary stat lines only, tested separately from secondary gifts, since any primary can pair with any gift). Current lines:
  - **Balanced**: basic `4/1/20/2`, Hermes `4/1/20/3`, Cyclops `4/1/23/0`.
  - **Defence-leaning**: Athena `3/3/20/5`, Poseidon `2/3/23/2`, Medusa `2/3/21/3`.
  - **Offence-leaning**: Ares `5/1/19/1`, Atalanta `5/1/18/2`, Achilles `6/1/16/1`, Minotaur `6/0/21/0`.
  - **Odysseus** `3/1/20/4` plus a bonus skill point.
  - (All as attack/armour/HP/intellect.)
  - **The lessons, worth remembering when adding one**:
    - Under flat armour subtraction, **one point of attack or armour is worth far more than several points of HP**. The two ancestries that started at 3 attack (basic and the old Cyclops at `3/0/25`) survived about a quarter to a third as often as everyone else, and armour `0` was brutal.
    - **Starting armour of 4 or more let a zero-skill player past the Minotaur** (deliberately a skill-point gate: a player who has invested no skill points should almost certainly not get past him), so defence lines trade armour for HP instead.
    - **Intellect is currently close to free**: it only gates the empty Trophy Room. Paying for a stat with low intellect isn't a real cost yet.
- **Secondary ancestor, built - see "Secondary ancestry abilities" below for the full system.** `choose_secondary_ancestry(primary_key)` prompts for a second figure, excludes `primary_key` from the printed list, and rejects re-typing it (reprompting with a dedicated message) - **the same figure can never be picked as both**. `create_player()` takes a required third parameter, `secondary_ancestry_key`, and applies its `secondary_effect` - unless it matches `ancestry_key` or is `"basic"` (whose `secondary_effect` is `None`, the deliberate "skip entirely" option). **No stat effect from the secondary pick, ever** - only a `Character` ability flag.

## Secondary ancestry abilities
- **Ten flags on `Character`** (`characters.py`, all default `False`), one per non-`"basic"` ancestry, granted once at character creation via `ANCESTRIES[key]["secondary_effect"](player)` - never touched by the skill tree, and deliberately disjoint from its four ability flags (`has_double_strike`, `has_last_stand`, `has_thorns`, `dodge_chance`).
- `has_reckless_strength` (Ares) - `Character.get_miss_chance()`: halves the heavy-attack miss chance, applied last (after the blade modifier and armour weight), so `0.2` unarmed, `0.15` with a blade. It used to remove the miss chance entirely, but a balance simulation found guaranteed 1.75× damage let a zero-skill-point player beat the Minotaur every time with heavy attacks.
- `has_measured_casting` (Athena) - `handle_combat_command()`'s `cast` branch (`combat.py`): a cast never sets/is blocked by a cooldown. **Mana is still required and still deducted normally** - this flag touches only the cooldown check, not the mana check; don't let the two get coupled again (see the bug note below).
- `has_swift_feet` (Hermes) - `flee_combat()` (`combat.py`): short-circuits to a guaranteed clean escape before the per-enemy free-hit loop even runs, still marking every living enemy `has_been_fled_from = True`.
- `has_unyielding_tide` (Poseidon) - `Character.equipment_defence()`: a worn piece counts `if piece.durability > 0 or self.has_unyielding_tide` - a broken piece's `defence` keeps counting. Durability itself still degrades normally; only the defence-loss consequence is suppressed.
- `has_berserking` (Achilles) - `Character.attack()`: `+2` to `base_damage` when `self.hp <= self.max_hp / 2`, applied before the heavy multiplier (same point as `weapon_bonus`).
- `has_silver_tongue` (Odysseus) - `trade_with_ally()` (`exploration.py`): required items are never actually removed from the player's inventory, though the trade still completes (`trade_completed = True`) and the reward is still granted. Deliberately scoped to trades only - `recruit_companion()` was **not** given the same exemption.
- `can_ranged_without_weapon` (Atalanta) - `handle_combat_command()`'s `attack` branch (`combat.py`): the `attack ranged` weapon-equipped check is skipped. `Character.attack()` itself is unchanged - with no weapon equipped, `weapon_bonus` is just `0`, same as it always was.
- `has_petrifying_gaze` (Medusa) - `Character.attack()`: after a non-lethal hit, a 15% chance (`random.random() < 0.15`) to also apply a 3-turn Poison to the target via `apply_status_effect()`. Sits *after* the death-message early-return, so a killed target can never be poisoned by the same hit.
- `has_bull_rush` (Minotaur) - `Character.attack()`: `incoming += 3` when `target.hp == target.max_hp` - added to the first hit *after* the heavy multiplier, so it's never scaled by it, and never feeds into Double Strike's second hit (which reads `base_damage`). It used to be added to `base_damage` before the multiplier (+5 on a heavy opener), which let zero-skill players past the Minotaur about half the time.
- `has_iron_hide` (Cyclops) - `Character.take_damage()`: `reduced = max(0, reduced - 1)`, applied after armour, before the minimum-damage floor and the Last Stand/Thorns checks - so Iron Hide can never reduce a landed hit below `MINIMUM_DAMAGE`.
- **`Player.secondary_ancestry_label: str`** (default `""`) - set by `create_player()` to `secondary_data["secondary_ability_label"]` (the ability's *description*, e.g. `"Reckless Strength - heavy attack miss chance halves"` - **not** `secondary_data["label"]`, the ancestry's own name; see bug note below). Shown as a `"Secondary gift: ..."` line in `Player.get_stats()`, omitted entirely when empty.
- **`dev set <flag_name> 1`** (the existing, unmodified generic `dev set` command) happens to work for granting any of the ten flags directly, since `setattr` doesn't care that the value arrives as `int` rather than `bool` - useful for playtesting a specific ability without redoing character creation. See `dev_guide.md`.
- **Two more real bugs, found and fixed during the later balance pass that reworked Reckless Strength and Bull Rush above**: (1) the new `miss_chance` variable was computed but the `if` still compared against `HEAVY_ATTACK_MISS_CHANCE`, so Reckless Strength silently did nothing. (2) Bull Rush's `+3` was moved below the line that computes `incoming` but still added to `base_damage`, so it no longer affected the main hit at all - only a Double Strike second hit got +1 (`3 // 2`). Both regression-tested in `test_characters.py`.
- **Four real bugs found and fixed while building this** (see `roadmap.md`'s Completed entry for the full writeup): (1) the `cast` branch's mana check was nested inside a condition that made it unreachable for every player, not just `has_measured_casting` ones - fixed by keeping the cooldown check (guarded by the flag) and the mana check (always enforced outside the practice chamber) independent. (2) `has_reckless_strength` was declared and grantable but never actually read anywhere - the heavy-miss roll was unconditional until the flag was added to its condition. (3) A typo (`has_silver_tonuge`) in Odysseus' `secondary_effect` meant Silver Tongue could never trigger. (4) `create_player()` stored `secondary_data["label"]` instead of `secondary_data["secondary_ability_label"]` into `secondary_ancestry_label`, so the stats screen's "Secondary gift" line just repeated the ancestry name instead of describing the ability.

## Save/load system and the title screen
- **`save_system.py`, now built** - owns serialisation/deserialisation and file I/O only, nothing about prompts or routing (that's `character_creation.py`/`engine.py`, below). `PROFILE_LIMIT = 3`, `SAVE_SLOTS_PER_PROFILE = 5`, `SAVES_DIR = "saves"` (monkeypatched to `tmp_path` in every test that touches it - see `test_save_system.py`). One JSON file per slot: `saves/profile_N/slot_N.json`.
- **`serialise_player()`/`player_from_save_data()`** snapshot/reconstruct the full `Player`: stats (armour saved as `base_armour`, never the total - worn gear is re-equipped on load and counts itself), every one of `ABILITY_FLAG_NAMES`'s 13 boolean flags (the 3 skill-tree ones plus the 10 secondary-ancestry ones - the fourth skill-tree ability, `dodge_chance`, is numeric, handled as its own field instead), skill tree unlock counts + points, gold/level/XP/mana, both ancestry labels, `visited_floors`, `visited_rooms`, `dev_mode`, `auto_map`, `seen_hints`, known spells + cooldowns, active effects, inventory (name/equipped/durability), and companion (via `serialise_companion()` - see "Companion duels and levelling"). Bypasses ancestry selection entirely on reload - every stat is already known.
- **`serialise_room()`/`apply_room_data()`/`serialise_world()`/`apply_world_data()`** snapshot every room's mutable state (surviving enemies' HP/fled-status, current item list, completed trades) and patch a freshly-built `world.py` `Map` to match. **Every room gets a full snapshot on every save, not just changed ones** - a deliberate simplification over a delta model (see `save_system.py`'s own module docstring: real change-tracking would need a proper `Room.touched` flag, and JSON size for a text-game map is trivial, so this isn't a shortcut that needs revisiting urgently).
- **Locked exits are round-tripped as `"locked_exits"`** - the directions still locked, since a door opened once stays open (see "Locked exits open for good"). The older `unlocked_extras`/`locked_exits_removed` placeholders are still written, always empty - `test_save_system.py`'s `test_serialise_room_locked_exits_are_not_captured` pins that.
- **Enemies are restored by claim-then-rebuild**, in `apply_room_data()`. `serialise_room()` saves every living enemy's name, HP, fled-status and `wave_gate` (the *name* of the phase its `wave_gate_factory` would spawn, since a function can't be saved). On reload:
  - **Claim**: each saved enemy first claims an unclaimed same-named enemy already in the freshly built room, in order - so two same-named enemies (Medusa's pair of Gorgons) each get their own saved HP instead of colliding. Claiming keeps `build_world()`'s own instance, which matters for enemies `ENEMY_REGISTRY` doesn't know, like the Practice Chamber's dummy.
  - **Rebuild**: a saved enemy the fresh room doesn't have - a wave add or a later boss phase spawned mid-fight - is rebuilt from `ENEMY_REGISTRY`, or silently skipped if the registry doesn't know it either (only the dev test boss's lambda-built adds and phase 2 fall in that gap).
  - **Remove**: fresh enemies nobody claimed were defeated before the save, so they're removed.
  - **Re-link**: a saved `wave_gate` is looked up in `ENEMY_REGISTRY`, giving every reloaded sibling the same factory object, so `handle_enemy_defeat()`'s identity check still treats them as one wave.
  - *(A real bug found and fixed here: `apply_room_data()` used to only update enemies already in the fresh room and drop the rest. Fleeing partway through the Medusa chain and then saving reloaded the Lair **empty** - the Gorgons, Medusa (Awakened), Serpent's Kiss and the guard on `descend` all lost, so the boss could simply be skipped. Name-only matching also meant two same-named enemies would collide. Regression-tested in `test_save_system.py` (a full mid-wave world round trip) and `test_engine.py` (flee → save → load through `main()`).)*
- **`choose_title_screen_action()`, `choose_profile()`, `choose_slot()`, `choose_occupied_slot()`, `confirm()`** (`character_creation.py`) drive every save/load prompt. `choose_slot()` lists all `SAVE_SLOTS_PER_PROFILE` slots (occupied ones show their `slot_summary()`, empty ones show "empty") and lets you pick any of them. `choose_occupied_slot()` returns `None` (with a "Profile N has no saves" message) when the profile is empty, rather than ever letting an empty slot be picked - only Load Game needs this variant (see the bug note below).
- **Title screen** (`main()`, `engine.py`) - New Game / Load Game / Delete Save / Quit, looped until New Game or Load Game actually starts a session (Delete Save and Quit either loop back or exit). New Game prompts profile then slot, confirms before overwriting an occupied one, then proceeds into the existing name/ancestry flow unchanged. Load Game prompts profile then an *occupied* slot, rebuilds the world fresh, then patches in the save via `load_game()`. Delete Save prompts profile then occupied slot, then confirms - **only per-slot deletion is wired up**; `delete_profile()` (whole-profile) exists in `save_system.py` but nothing in `main()` calls it yet.
- **Session state**: `main()` tracks a single `active_profile`/`active_slot` pair, set by New Game, Load Game, or any confirmed mid-game `save <profile> <slot>`/`load <profile> <slot>`. Bare `save` and autosave both always target whichever slot is currently active.
- **Mid-game commands**: bare `save` (active slot, no confirmation), `save <profile> <slot>` (confirms only if that slot is occupied, then re-points the active slot to match), `load <profile> <slot>` (always confirms - *"Loading will discard any unsaved progress..."* - even when reloading the currently active slot; an empty target slot errors without prompting). **All three load paths build a fresh world first** - Load Game, the reload after death, and mid-game `load` all call `build_world()` (rebinding both `dungeon` and `all_floors`) before `load_game()`, which only ever patches a freshly built world. *(A real bug found and fixed: mid-game `load` used to pass the live, already-played `dungeon` straight to `load_game()`, so state the save never had leaked through - e.g. a hidden exit revealed after saving stayed revealed, and a trade completed after saving stayed marked as completed even though the player's inventory reverted. Regression-tested in `test_engine.py`.)*
- **Autosave** fires the first time `Player.visited_floors` gains a floor not already in it (see "Canonical attribute names" above). Always targets the active slot, no confirmation, prints `"(autosaved)"`.
- **Real bug found and fixed**: the title screen's Load Game action originally called `choose_slot()` (lists every slot, empty or not) instead of `choose_occupied_slot()` - picking an empty slot reached `save_system.load_game()` on a nonexistent file and crashed the whole game with an uncaught `FileNotFoundError`, since the existing `if slot_num is None: continue` guard could never actually fire against `choose_slot()`'s `int`-only return type. Fixed by switching to `choose_occupied_slot()`, whose genuine `None` return now makes that guard do something. Regression-tested in `test_engine.py`.
- **`save`/`save <profile> <slot>`/`load <profile> <slot>` are real player commands** - listed in both `get_controls_text()` and the README's Controls section, same as every other real command.
- **Death now offers a reload instead of always ending `main()`.** The per-life game loop is wrapped in an outer `while True:` - on death, `confirm("You have died. Reload your last save?")` decides whether to reload the active slot fresh (a new `build_world()` plus `load_game()`) and `continue` playing, or fall through to the `"You have died."` message and `return`. Since both New Game and Load Game always set `active_profile`/`active_slot` before the game loop is ever reached, this prompt always fires on death - a player who never manually saved reloads back to whatever the last autosave captured, not a blank slate. **Real bug found and fixed**: the inner loop's own exit condition (`while player.is_alive():`) couldn't tell a `quit`/`exit` break apart from an actual death - both fell through to the same death-reload check, so quitting normally falsely triggered "You have died. Reload your last save?". Fixed with a `quit_requested` flag, set only by the `quit`/`exit` branch and checked immediately after the inner loop - `return`s before the death-reload logic ever runs. Regression-tested in `test_engine.py`.
- **Planned, not built: hardcore mode** (roadmap.md's "Hardcore mode" item, still needing a full design pass). Permadeath, on the hardest difficulty setting, so it waits on the difficulty system. Prometheus offers it once, on first meeting (Forge of Prometheus, floor 2); declining means he never offers again. Two constraints are already clear. The once-only offer has to be per-save state on `Player` (like `seen_hints`), so it survives save/load. And it must be data on the `Ally`, never an `if ally.name == "Prometheus"` check. The big open question is how permadeath changes the death-reload flow above - skip the reload prompt, delete the save, block `load`, or some mix.

## Multi-stage boss fights
- **No dedicated `Boss` class** - a boss is still a plain `Enemy`. `next_phase_factory` (a callable, following the existing `create_*()` factory pattern) is checked first in `handle_enemy_defeat()`: instead of removing the enemy and granting loot/rewards, it removes the current phase, adds `next_phase_factory()`'s result to the room, and sets `player.in_combat = True`/`player.current_target = next_phase` - **the transition is seamless**, combat never unlocks, the player doesn't need to re-attack. Returns `"<name> falls, but something rises to take its place - <next phase's name>."`.
- **`next_wave_factories`, built as an extension on top of `next_phase_factory`** - a `list[Callable[[], Enemy]]`. When set, `handle_enemy_defeat()` checks it *before* `next_phase_factory`: it removes the phase, spawns every factory's add into the room, sets `current_target` to the first add, and returns `"<name> falls, but conjures <n> lesser foes to bar your path!"` - the phase transition itself is deferred, not skipped. Every spawn message (wave, phase transition, and wave-gated transition alike) also appends the newcomers' `description` lines, one per distinct add name, so a pair of identical Gorgons gets a single line.
- **`wave_gate_factory`, set only by `handle_enemy_defeat()` itself, never by content directly** - each add spawned via `next_wave_factories` gets its own `wave_gate_factory` set to the phase's `next_phase_factory` (the deferred transition, now carried on the adds themselves rather than tracked on `Room`/`Player`). When a `wave_gate_factory`-tagged enemy dies and reaches the normal (non-phase, non-wave) defeat path, `handle_enemy_defeat()` (which has already removed the dying add from the room) checks `room.enemies` fresh for any *remaining* sibling sharing that *same* factory (`is`, not `==` - two visually-identical lambdas are still different objects) - alive **or dead**. A dead sibling still in the room simply hasn't been processed yet, and `resolve_pending_defeats()` is about to process it, so it's that sibling's own defeat that triggers the spawn. Only once no sibling remains does `wave_gate_factory()`'s result actually spawn, appending `"The last of them falls - something greater emerges: <next phase's name>."` to the existing reward messages. **Correct regardless of kill order, and fires exactly once** - even when a whole wave dies in the same round (one add to the attack, another to Thorns). Counting only *living* siblings would have let the first of two same-round deaths spawn the phase, with the second spawning it again.
- **`create_test_boss()`** (`content/dev_content.py`, dev-only) exercises the whole chain end-to-end: Test Boss (hp 1) → defeat spawns two Test Adds (wave) → the first add's defeat alone does nothing (sibling still alive) → the second add's defeat triggers the deferred transition → Test Boss (Phase 2) (hp 1, no further factories) → its own defeat ends combat normally, with its own gold/XP reward. Registered in `ENEMY_REGISTRY` as `"test boss"` - reachable via `dev spawn test boss`, and still kept around for isolated testing without a full room/fight. **A real, named equivalent now exists**: Medusa (`create_medusa()`, `content/floor_4.py`, Lair of Medusa) - defeating Medusa (Phase 1) spawns two Gorgons (`next_wave_factories`), clearing both triggers the deferred transition to Medusa (Awakened) (`next_phase_factory`), which also carries `has_petrifying_gaze=True` - the first `Enemy` built with that flag set directly, rather than only ever granted to the player via a secondary ancestry (see "Secondary ancestry abilities" below). Hades and Typhon are still unplaced.
- **Real bug found and fixed while building this**: `resolve_attack_and_check_defeat()` always cleared `player.current_target` to `None` before calling `handle_enemy_defeat()` for each newly-defeated enemy, relying on `handle_enemy_defeat()` to re-set it - but only the phase-transition/wave branches ever did. A normal defeat in a multi-enemy fight (no transition) left `current_target` genuinely unset until the player's next `attack`/`target` command, even though the room still had living enemies and combat correctly stayed locked. Fixed by auto-selecting the next living, still-relevant enemy (`still_relevant_enemies` - the same `respawns`-excluding list already used for the "is combat still going" check) whenever `current_target` is still `None` after the defeat loop. Regression-tested in `test_combat.py`/`test_engine.py`. (That loop has since been replaced by `resolve_pending_defeats()` - see "Defeat handling" - which keeps the same guarantee: a still-living current target is kept, otherwise it moves to the first survivor.)
- **Medusa's own stats went through a real playtesting-driven rebalance, not just placement.** Original tuning (Phase 1 `attack_damage=8`, Awakened `attack_damage=9`/`heal_amount=6`/`brace_amount=4`/`caution_weight=1.8`) turned out to make Awakened's fight a near-binary pass/fail gated by which skill-tree path the player had invested in, rather than a genuinely hard-but-winnable fight - a pure-Defence build was safe, everything else was close to unwinnable, because armour is a flat subtraction and her `attack_damage` sat right at a threshold only one specific build cleared. **Current values**: Phase 1 `attack_damage=6`; Awakened `attack_damage=8`, `heal_amount=2`, `brace_amount=2`, `caution_weight=1.2` - confirmed via simulation to be winnable across every realistic skill-point allocation a player has by that point, not just one. The lesson worth remembering if she's ever retuned again: her own `attack_damage` matters far more than `heal_amount`/`brace_amount` for whether a given build survives, since it's what sets the armour threshold below which every hit costs real HP.

## Testing main() — refined now that monkeypatch is approved
`main()` is no longer entirely off-limits, but it's tested differently from everything else, and sparingly.
- **A small number of end-to-end smoke tests are worth having** — using `monkeypatch.setattr("builtins.input", ...)` fed from an iterator of scripted commands, plus `capsys` to capture output. These test the whole routing chain in one go (input parsing -> dispatch -> the real handler -> the printed result), which unit tests on individual handlers can't catch.
- **This is a genuinely different category from every other test in this project** — an integration/smoke test, not an isolated Arrange-Act-Assert unit test.

## Story premise
- **What the player is told**: Hades has stopped judging the dead. Souls pile up unsettled in Asphodel, and the monsters of the deeper
  levels roam free. An ancient oath keeps the gods out of his halls - floor 2 is as far as their reach extends - so they send mortal
  heroes down to make him answer for it. Athena delivers this on floor 2; Ares and Hermes only refer back to it.
- **The truth (revealed on defeating Hades, floor 8)**: Hades broke the law because he was spending all his power holding Tartarus
  shut against Typhon. Defeating him frees Typhon, and the hero must now stop Typhon in Tartarus (floor 9).
- **Consequences for writing dialogue**: the gods genuinely believe Hades is at fault - their lines should never hint otherwise.
  Foreshadowing belongs on floor 7 (the Oracle, Persephone), and must read as ambiguous before the reveal.
- **Mechanical hooks (half built)**: the reveal will use the generic `Enemy.defeat_effect` hook (built, first used by Achilles' duel) on Hades'
  final phase, never a name check. Still to do: guarding Hall of Hades' descend, so Tartarus is only reachable after Hades dies. The ending after Typhon is still undecided.
  Both hooks are roadmap.md's "Story reveal hooks" item, placed ahead of "Populate all floors" so floors 7-9 can be written around them.
